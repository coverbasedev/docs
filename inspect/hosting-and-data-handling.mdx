Inspect runs on the same platform, in the same region, under the same encryption, tenancy and retention controls as the rest of Coverbase. This page covers only what is specific to Inspect: the browser host, the models, and the evidence it produces. For the platform controls, see [Data protection](/security/data-protection) and [AI governance](/security/ai-governance).

<Info>
  Technical details on this page were last reviewed in September 2026 against the current release. Ask your Coverbase team if you need confirmation for a specific date.
</Info>

## Components and where they run

| Component | Where it runs | Operated by |
| --- | --- | --- |
| Coverbase application, database, object storage, workers | AWS, United States (`us-east-1`) | Coverbase |
| API evidence requests | Coverbase workers in the same AWS environment | Coverbase |
| Browser sessions for browser evidence and sign-in | Browserbase, a managed browser service, US region | Browserbase, under Coverbase's account |
| Models | AWS Bedrock, through Coverbase's AWS account | AWS |
| Credentials and secrets | AWS Secrets Manager under AWS KMS keys, in Coverbase's account | Coverbase |

Inspect uses Chrome hosted by Browserbase, with safeguards applied by Coverbase. Coverbase workers control each session over the Chrome DevTools Protocol and install the read-only safeguards described in [Safeguards and limits](/inspect/safeguards-and-limits) once sign-in completes. Browserbase is on Coverbase's subprocessor list, available on request.

### Coverbase-operated browser hosting: under investigation

Coverbase is evaluating whether to operate Inspect's browser sessions on its own infrastructure, so that browser hosting and session recording would sit inside the same boundary as the rest of the platform. This is an investigation, not a committed change. It would be Coverbase-hosted, which is distinct from a customer-hosted or on-premises deployment; neither is offered today. If either matters to your program, raise it during evaluation so it can be discussed on its own terms.

## What Browserbase sees

Because the browser itself runs at Browserbase, anything that passes through a browser session passes through Browserbase's infrastructure. Anything that stays on the API channel or in Coverbase's secrets store does not.

| Item | Passes through Browserbase? | Notes |
| --- | --- | --- |
| Admin console pages the agent visits: text, structure and any data shown on them | Yes | The browser renders them; Coverbase reads them over the DevTools Protocol. Not redacted. |
| Evidence screenshots | Yes, captured in the browser | Stored by Coverbase in its object storage; see below. |
| Session recordings (replays) | Yes, recorded and stored by Browserbase | Played back inside the Coverbase dashboard. |
| Session cookies and tokens the application sets after sign-in | Yes | They live in the browser session. When a sign-in profile is kept for reuse, it is stored as a Browserbase context. |
| Passwords and usernames used for browser sign-in | Yes, at the moment of entry | Resolved from Coverbase's secrets store by the runtime and typed into the sign-in form. Not shown to the model. |
| One-time codes | The generated code only | The seed stays in Coverbase's secrets store; the six-digit code is generated by Coverbase and entered into the form. |
| Passkeys configured for a sign-in | Yes, the credential is loaded into the session's virtual authenticator | The stored key is held in Coverbase's secrets store and loaded into the browser session for the duration of the run. |
| Identity-provider sign-in through a stored profile (Okta, Entra) | The session cookies only | The service-app keys Coverbase uses to talk to your identity provider are used from Coverbase servers, not from a browser session. |
| API credentials: bearer tokens, OAuth client secrets | No | Used only from Coverbase workers on the API channel. |
| Plans, observations, evaluations, findings | No | Written and stored by Coverbase. |

## Models

Inspect currently uses Anthropic Claude through AWS Bedrock, within Coverbase's AWS account. The browser agent, the sign-in agent, network and navigation adjudication, plan preparation and evaluation all run through Bedrock.

- **Cross-region inference.** Inspect calls Bedrock through a cross-region inference profile. A model request may be processed in a supported AWS region other than `us-east-1`. Requests and responses stay within AWS and within Coverbase's account.
- **No training on your data.** Customer data sent to Bedrock is not used to train the foundation models. See [AI governance](/security/ai-governance).
- **Invocation logging.** Coverbase keeps Bedrock invocation metadata (model, timing, token counts) for 90 days for capacity and reliability monitoring. Prompt and response text is not delivered to that log.

## What the models see

| Input | Sent to the model? |
| --- | --- |
| Vendor documentation, during plan preparation | Yes |
| The control's expectation and instructions | Yes |
| The admin console page the agent is on (text and structure), during a browser step | Yes |
| Evidence screenshots | No. Screenshots support human review; they are not currently supplied to the inspection model. |
| Credentials, one-time codes, passkeys | No. Factor values are resolved and entered by the runtime; the model chooses the field, not the value. |
| Outbound request bodies, during network adjudication | A reduced form: field paths and operation-like literals are kept; credentials, identifiers, long text and query values are replaced with redaction markers. |
| Navigation targets | The address path and query parameter names, never query values. |
| Collected observations | Yes, when a control is evaluated. The records that were collected are supplied so the model can grade them against the control's expectation and write the justification. |

## What is stored, where, and for how long

| Data | Where | Retention |
| --- | --- | --- |
| Observations, evaluations, comparisons, activity events | Coverbase database, scoped to your organization | Life of the subscription, under your agreement's retention terms |
| Evidence screenshots | Coverbase object storage, encrypted at rest | Retained with the inspection; no automatic expiry today. Deletion is available on request. Screenshots from an attempt that did not complete are deleted. |
| Browser session recordings (replays) | Browserbase | 30 days, Browserbase's retention period for Coverbase's plan. Played back inside Coverbase through Coverbase's API. |
| Stored browser sign-in profiles | Browserbase | Deleted after 12 hours without use |
| Target credentials, API tokens, one-time-code seeds, passkeys | AWS Secrets Manager under KMS | Until you rotate the secret or delete the target, which purges its stored secrets. Coverbase runtimes retrieve values to run inspections; credential-management APIs do not return stored values. |
| Bedrock invocation metadata | Coverbase AWS account | 90 days |
| Application logs | Coverbase logging | Platform retention. URLs are redacted before logging; no credential or page content is logged. |

## Redaction

- **Redacted:** URLs in logs and events; request bodies before the network adjudicator sees them; credentials and secrets everywhere.
- **Not redacted:** evidence. Screenshots and observed records are stored as captured, because they are the evidence a reviewer and an auditor need to see. If a control's evidence includes personal data (a member list, an email address in an audit log), that data is stored in Coverbase alongside the observation.

<Warning>
  Inspect does not strip sensitive values from evidence. Pick the control set with that in mind, or start with controls whose evidence is configuration rather than people.
</Warning>

## Residency

The multi-tenant Coverbase environment runs in the United States, and Inspect's browser host runs in its US region. Model requests are processed as described under Models above. Programs with a specific residency requirement should raise it during evaluation.
