You can bring a new application to Inspect using the same API and browser evidence collection that Inspect uses for other applications. The setup work depends on the access you can provide, the controls you want to check, and the evidence the application exposes.

If you are new to Inspect, start with the [Inspect overview](/inspect/index).

## What you need

- The application's name and sign-in address.
- The controls or control set you want to inspect.
- An account with permission to read the relevant settings, or credentials for the application's API.
- Any vendor documentation you have. API request planning requires API documentation; browser navigation does not.

Use a dedicated account with the least privilege needed for your checks. Enter credentials in Inspect when you configure access. Do not include passwords, tokens, or session cookies in an onboarding request.

## How Inspect collects evidence

The two collection methods have different documentation requirements:

| Method | How it works | What it needs |
| --- | --- | --- |
| Browser | The agent navigates the application and reads settings or records visible to the signed-in account. It can work without vendor documentation. | Working browser access and permission to view the evidence. Documentation can help guide navigation. |
| API | Inspect plans requests from the application's documented API operations and reads the returned records. | API documentation, supported authentication, and permission to read the required data. |

Documentation is required to plan API requests. Missing API documentation does not rule out collecting evidence through the browser. Both methods produce observations you can review alongside the control result.

An inspection still needs application setup and prepared plans before launch. If documentation is unavailable, contact Coverbase to confirm the collection path for your controls.

## Set up your first inspection

<Steps>
  <Step title="Add the application and configure access">
    Add the application in **Inspect**, identify the tenant you want to inspect, and configure its sign-in method or API access. Check that the account can reach the settings your controls ask about.
  </Step>
  <Step title="Choose your controls">
    Select a control set for the application. For example, you might check administrator access, MFA enforcement, or external sharing. Coverbase can help you choose checks that match the application's capabilities.
  </Step>
  <Step title="Check readiness">
    Review any preparation or access blockers before launching. Coverbase can help with initial application setup, documentation for API planning, and collection paths that need additional configuration.
  </Step>
  <Step title="Run and review">
    Review each control's result and its supporting observations. Browser evidence can include screenshots and session replay. Check incomplete or failed results individually to understand what could not be collected.
  </Step>
</Steps>

## When you need help

Contact your Coverbase team or [support@coverbase.ai](mailto:support@coverbase.ai). Include the application name, sign-in address, intended controls, and links to any relevant documentation. For a failed inspection, include its link and describe where collection stopped.

We aim to acknowledge onboarding requests within **one business day**. We then assess access, documentation, and the requested checks with you. If additional work is needed, we agree on its scope and a delivery estimate after that assessment. The acknowledgment target is not a promise that every application will be ready within one day. Your agreement governs contractual [support commitments](/security/support-and-slas).

Coverbase maintains the inspection runtime and shared application configuration. Your team maintains the account's permissions and credentials. If the application changes in a way that interrupts collection, contact Coverbase so we can investigate and agree on the next step.

## Coverage and limitations

The inspection experience is shared across applications. The evidence available for a particular control can differ:

- An application may not expose a setting, audit event, or record through either its API or interface.
- Permissions, subscription tiers, SSO policies, or network restrictions can limit what Inspect can reach.
- Pop-ups, unusual navigation, or authentication challenges can require engineering assistance. Turnaround depends on the issue and the access needed to reproduce it.
- An incomplete inspection needs investigation. Failure to find a setting does not by itself establish that the setting is absent or the control is inapplicable.

You can revise a plan's prose and browser instructions. Inspect does not provide a separate customer-facing connector SDK or no-code connector builder, and compiled API methods are not customer-editable. If you need a new collection method or authentication scheme, Coverbase scopes that work with you.

## Reducing setup work

Coverbase assists with initial application registration and API documentation preparation where needed. We are working on automatic application registration and on-demand documentation discovery, so Inspect can find and refresh the documentation needed for your controls. These are planned improvements to onboarding, not requirements for the browser agent to navigate an application.
