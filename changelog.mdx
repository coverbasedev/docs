## 2026-11-11: Intake review stages, legal entities by country and tax registrations per address

### New features

- **Review stages on intake requests.** An intake template can send each request through up to 10 stages in order, for example a category manager approval and then a third-party risk review. Each stage names its reviewers and whether it may send the request back or deny it. See [Intake review stages and request rules](/user-guides/intake-review-stages).
- **Require a vendor contact.** An intake template can make requesters name at least one contact at the vendor, with an email, before they continue. See [Require a vendor contact](/user-guides/intake-review-stages#require-a-vendor-contact).
- **Block requests for existing vendors.** An intake template can stop requesters starting a request for a vendor that is already approved or being onboarded. See [Block requests for existing vendors](/user-guides/intake-review-stages#block-requests-for-existing-vendors).
- **Legal entities by country.** A **Legal Entity** question can let requesters pick a country, which adds every active legal entity in it. See [Legal entity questions](/user-guides/questionnaires#legal-entity-questions).
- **A tax registration per address.** The supplier form's tax question has an **Address** pick, starting on **All addresses**, so a supplier with a different number at each address records one registration per address. Your team can do the same from the **Add Tax Registration** dialog. See [Tax registrations and addresses](/user-guides/supplier-information#tax-registrations-and-addresses).
- **Edit a person's name.** An admin can set the name a member shows under, from **Organization → People**. See [How people's names are shown](/user-guides/permissions-and-roles#how-peoples-names-are-shown).

### Changes

- Vendor search results on an intake request show **Approved supplier**, **Onboarding in progress** or **New supplier**, with the owners, and a lock line on a vendor the template blocks. See [What the labels on a vendor mean](/user-guides/requesting-a-vendor#what-the-labels-on-a-vendor-mean).
- A requester's answers are read-only once they submit, and reopen only when a reviewer sends the request back.
- A member with no name on file shows under a name read from a `first.last@` email address, with the email underneath.
- Legal entities chosen on an intake request are sent to your finance system under the supplier's main site, and each tax registration is sent with its address's external ID.
- More than three optional documents on a supplier portal request fold under **Optional documents**. Request Supplier Update explains how to turn on the portal's **Profile** page when it is off.

## 2026-11-11: Screening permissions in the role editor

### New features

- **A Screening row in the role editor.** Custom roles can now grant screening access: **Read** to view the queue and each vendor's **Screening** tab, **Update** to confirm and dismiss matches and screen people, **Export** for the CSVs, and the new **Configure** to change the screening settings. See [Screening permissions](/user-guides/permissions-and-roles#screening-permissions).

### Changes

- Members can now confirm, dismiss and allowlist screening matches, use **Screen now**, **Confirm & screen** and **Add individual**, and download the screening CSVs. Changing the screening settings stays with Admins.
- The screening settings follow the new **Configure** permission instead of the `integration` one. Connecting the provider account and switching provider still need `integration:update`. `PUT /v1/screening/settings` and `GET /v1/screening-profile-groups` now need `screening_match:configure:org`, and `GET /v1/screening/settings` needs `screening_match:read:org`.

## 2026-11-10: Sanctions screening evidence and thresholds

### New features

- **Per-screen and per-match exports.** The **Export** menu on the screening queue downloads every screen in the last 12 months, clear ones included, with the date of the lists it ran against; the failed screens alone; and every match with its decision, reviewer, decision date and reason. Through the API: `GET /v1/screening/run-export` and `GET /v1/screening/match-export`. See [Every screen, every decision](/user-guides/sanctions-screening#every-screen-every-decision).
- **Batch summary.** **Recent batches** on the screening queue shows how many subjects each sweep, re-screen and rename screened, matched, cleared and failed. Through the API: `GET /v1/screening-batches`. See [Batches](/user-guides/sanctions-screening#batches).
- **Thresholds per source and per risk level.** The match threshold can be set overall, for each source, and for each monitored risk level. See [Settings](/user-guides/sanctions-screening#settings).
- **Re-screen every vendor.** An administrator can screen every enrolled vendor and person at once, after confirming how many screens it will run.
- **Renamed vendors are screened straight away.** A vendor whose name changes is screened under its new name within minutes.

### Changes

- A decision on a screening match needs a written reason, unless an administrator turns off **Require a reason for every decision**.
- Each screen records **Lists as of**, and a sanctions match names the program it is listed under.
- Screening runs and matches carry your vendor's external ID, in the app, the CSVs and the API.
- Changes to the screening configuration, monitoring rules, profile groups and workspace default cadence are written to the system audit log.
- Administrators are notified when the OFAC lists used by the intake check could not be refreshed for more than a day.

- A rule scoped to some agents does not apply to any other agent, so a baseline for one agent keeps every other agent off that target and out of its tool list. See [All rules](/products/agent-governor#all-rules).

## 2026-11-06: Due diligence from Ironclad workflows

### New features

- **Ironclad workflows start due diligence.** Pick the Ironclad templates that start third-party due diligence. A launched workflow opens an intake request for its vendor, and the business owner who launched it is emailed the inherent risk questionnaire, drafted from the workflow. Renewal and amendment templates open a review against the existing vendor. See [Ironclad](/integrations/guides/ironclad).
- **The result goes back to Ironclad.** When due diligence completes or the request is declined, Coverbase writes the status, decision, risk tier and a link onto workflow fields you choose, comments on the workflow, and can approve an approver role.
- **Executed contracts file under the vendor.** A completed workflow's executed record and signed copy file under the vendor its request was for.

### Changes

- Ironclad connects with an OAuth client and the Ironclad user Coverbase acts as. Existing API token connections keep working.
- **Register webhook in Ironclad** subscribes Coverbase to workflow and contract events in one click, and Coverbase verifies Ironclad's own signature on each delivery.
- An executed Ironclad record is now marked executed even when its status and signed copy are read from the same field.

## 2026-11-05: Policy sets, organization settings and MCP sign-in

### New features

- **The Broker is now the Agent Governor.** The page is at **Inspect › Governor**, its settings at **Configuration › Agent Governor**, and the API at `/v1/governor/`. Old links, and agents and gateways set up with `/v1/broker/` paths, keep working.
- **Policy sets and the library.** Group governor rules into named sets applied to every target or chosen targets, and install from a library of 28 sets mapped to SOC 2, ISO/IEC 27001, ISO/IEC 42001, the EU AI Act and more. See [Policy sets](/products/agent-governor#policy-sets).
- **Governor organization settings.** Hold and deny thresholds, risk floors by intent, a session guard against read then exfiltrate, named approvers, two-person approval and agent defaults, with a preview of what a change would do. See [Organization settings](/products/agent-governor#organization-settings).
- **Sign in from MCP clients.** Claude Desktop, Claude Code, Cursor and VS Code can sign in to the governor with OAuth instead of a key, acting on your behalf. See [Sign in from an MCP client](/products/agent-governor#sign-in-from-an-mcp-client).
- **MCP servers on your machines.** `cbg-gateway discover` reports the MCP servers your people's AI clients are configured with. Review, approve, block and pin their tools. See [MCP servers](/products/agent-governor#mcp-servers).
- **Read-only MCP server audits.** `cbg-gateway audit` shows what each server's tools do, what kinds of data they return, how they handle bad input and how the server signs people in, and Coverbase audits public HTTPS servers on a schedule. See [Audit a server](/products/agent-governor#audit-a-server).
- **Regions.** Pin a governor target to a region, and its actions run only on a gateway in that region. See [Regions](/products/agent-governor#regions).
- **SPIFFE identities.** Agents can sign in with a SPIFFE JWT-SVID.
- **Code sandboxes.** Agents run Python, JavaScript or bash in a fresh Blaxel sandbox for each action, with network access off by default, masked output and the same approvals as every other action. See [Code sandboxes](/products/agent-governor#code-sandboxes).
- **Agents as an identity provider.** An agent can get a short-lived signed token that names it and the person it acts for, and your services verify it against your organization's published keys. See [Agents as an identity provider](/products/agent-governor#agents-as-an-identity-provider).
- **Trend lines** on every Inspect Overview number.
- **Prompt injection classifier.** The governor scores requests, results and MCP tool descriptions for prompt injection with Amazon Bedrock Guardrails and a local model, raises the risk of a flagged request, and masks or withholds a flagged result. See [Prompt injection classifier](/products/agent-governor#prompt-injection-classifier).

### Changes

- Vendor audit logs are read every 15 minutes by default, and you can choose 2, 5 or 60, or **Sync now**.
- The MCP endpoint answers a client that accepts only an event stream with one.
- Inspect and Governor pages fit a phone screen.
- **Server shell access** now runs only read-only diagnostic commands on their own, and **Kubernetes clusters** holds workload changes for a person. See [Library](/products/agent-governor#library).
- An MCP client signed in with OAuth reaches only the targets you approved, and two-person approvals take the narrower of the two approvals. See [Approvals](/products/agent-governor#approvals).
- Named approvers must be able to manage the governor, and a library rule you delete stays deleted when the set updates.

## 2026-11-04: Screening cadence and monitoring rules in Coverbase

### New features

- **Profile groups on the settings page.** Create, edit, prioritize and archive screening profile groups under **Configuration → Monitoring → Screening**, with a cadence per source. You no longer need to ask Coverbase to set one up. See [Profile groups](/user-guides/sanctions-screening#settings).

## 2026-11-04: The Governor, runtime authorization for every agent

### New features

- **Governor (beta).** Inspect gains a **Governor** console that puts Coverbase in the request path of any agent, yours or a vendor's, and authorizes each action at the moment the agent takes it: it classifies the action's intent and risk, applies the target owner's policy, mints a credential scoped to exactly that action and a short lease, masks sensitive data in the response, records every decision in a per-organization tamper-evident trail, and can stop any agent at once. Four enforcement tiers cover agents from those called inline through to vendor copilots watched only in their own audit logs. A policy simulator replays recent decisions against a draft rule set before you save it. Behind the `agent-governor` gate. See [the Governor](/products/agent-governor).

## 2026-10-21: Bank account currency, Mexico and Colombia payment details

### New features

- **Account currency in the form.** Every bank form asks for the account's currency, opening on the bank country's own. The API already accepted and returned `currency`.
- **Mexico's payment system.** Mexican accounts take `payment_system`, `spei` or `spid`, and `beneficiary_name`, both required. See [field keys](/api-reference/supplier-profile#bank-account-values).

### Updates

- **Colombia.** Accounts require `beneficiary_name`, `bank_name`, `bank_code` and `account_type`. - **Clearer refusals in the form.** A refused bank save lists every reason beside **Save** as well as under each field.

## 2026-10-16: Finance system ids, inactive addresses and Colombian registration details

### New features

- **Finance system ids on addresses and contacts.** Sites accept and return `external_id`, and [`PUT /v1/vendors/{vendor_id}/contacts/external_id`](/api-reference/supplier-profile#set-a-contacts-finance-system-id) stores your finance system's id on a contact. [`GET /v1/vendors/{vendor_id}/contacts`](/api-reference/supplier-profile#list-contacts) lists contacts with their ids.
- **Inactive addresses.** Sites accept `is_inactive` and return `inactive_at`. An inactive address stays on file. A supplier who moves can file a new address in the portal and keep the old one as inactive.
- **Registration details.** Tax registrations accept and return `details`, the country's registration fields beside the number. Colombia's include `nature`, `legal_entity_type`, `document_type`, `dv` and `ciiu`, and its NIT is now sent without the verification digit.

### Updates

- **IBAN checks.** An IBAN must start with its bank's country code, and a bank or branch code that does not match its position in the IBAN is refused. Countries that do not issue IBANs no longer collect one.
- **Intermediary bank in every country**, with country code, city, account number, bank name, branch number, IBAN and SWIFT/BIC. The country code and account number are required once any of them is sent. See [field keys](/api-reference/supplier-profile#bank-account-values).
- **Peru.** `branch_code` and `account_number` are entered beside the `cci` again and checked against it.

## 2026-09-05: Review a vendor's attributed estate

Security Intelligence now shows every domain and address it attributes to a vendor as a list you can correct, and every finding carries the step that resolves it.

### New features

- **Attributed estate.** The Security tab lists every asset the scan attributes to the vendor, with when each was first and last seen. Filter to what still needs a decision, and **Confirm** or **Dispute** each one from its row. A disputed asset leaves the next scan and the rating; withdrawing the dispute puts it back. See the [security intelligence guide](/user-guides/security-intelligence#attributed-estate).
- **Add the assets the scan cannot find.** Discovery reads certificate transparency, so a host with no public certificate never appears. **Add asset** puts them in the estate, one per line or comma-separated, and the next scan probes and scores them like any other. One submission costs one rescan however many hosts it carries, and assets you add survive a scan that cannot see them.
- **Remediation on every finding.** Opening a finding shows what was observed, whether it cost the rating points and how many, how long it has been open, and the step that fixes it. Forwarding one to a provider now hands them the change to make rather than the problem to research.
- **Generate findings in bulk.** **Generate findings** raises a tracked finding for every scored issue at once, ticked by default and ordered by severity, for the sweep that turns up the same problem on a dozen hosts.
- **Transport checks per host.** TLS is measured on each attributed host rather than only the vendor's main domain, so one neglected server does not hide behind a well-configured front door.

### Fixes

- DNSSEC, TLS reporting and email authentication no longer read as failures for domains that have not adopted them. Non-adoption is now recorded as an observation rather than scored like a misconfiguration, and DNSSEC is read from the signed zone rather than from the resolver's answer.

- **Radar API.** Create radar events (`POST /v1/radar/events`), list and retrieve events, and list, retrieve, dismiss, and undismiss radar alerts. Dismissing with `suppress_similar` teaches the detector to suppress similar alerts going forward. See the [Radar API reference](/api-reference/radar).
- **Reassessments API.** Create a reassessment from a radar event with its vendors, curate the vendor set (add vendors, opt vendors in/out), set the assessment plan, then `confirm`, `dismiss`, or `run` it. - **Radar & reassessment webhooks.** Subscribe to `RadarEvent.*`, `RadarDetectorResult.*` (radar alerts), and `Reassessment.*` events. `*.Updated` events carry per-field `field_diffs`; soft-archives surface as `*.Deleted`. See the [event catalog](/integrations/webhooks#event-catalog).

### Updates

- **MCP & AI assistants.** The Coverbase MCP server can now read reassessments (`query_radar` kind `reassessments`) and create radar events, dismiss alerts, and create/update reassessments (`mutate`). The in-product Interrogate assistant can propose the same radar/reassessment actions on a vendor.

## 2026-05-22: This week at Coverbase

A big week for the public API: self-serve key management, deeper workflow visibility, automatic webhook delivery, and tighter network controls.

### New features

- **Self-serve API key management.** Admins can now list, create, rotate, and revoke their org's `ak_*` keys without filing a support ticket. Rotation is atomic, so you'll never have two valid keys live at the same time. See the [API Keys reference](/api-reference/api-keys).
- **Scoped admin API keys.** Admins can mint long-lived `ak_*` keys carrying the `keys:manage` and/or `audit:read` scopes, so key management and audit-log reads can run headlessly, without a short-lived dashboard JWT. The admin-JWT path is unchanged and still works. Granting scopes stays an admin-only action (a scoped key cannot grant scopes to itself or any other key), and a key missing the required scope gets `403 insufficient_scope`. See [API key scopes](/conventions#api-key-scopes).
- **List workflow runs.** Page through workflow run history with filters for workflow name, status, and time range. No need to know a run ID up front. See [List workflow runs](/api-reference/workflows#list-workflow-runs).
- **Archive an assessment via API.** `DELETE /v1/assessments/{id}` mirrors the in-product Archive action: it soft-deletes the assessment along with its evals and findings, closes the portal if open, and cancels any in-flight workflow runs. See [Cancel (archive) an assessment](/api-reference/assessments#cancel-archive-an-assessment).
- **Public API audit log.** Every authenticated `/v1/*` call is now recorded and visible to admins under **Settings → Audit log** (Integrations group), or via `GET /v1/system_audit_log`. Request and response bodies are never persisted. See [Public API audit log](/conventions#public-api-audit-log).
- **Org-level API IP allowlist.** Restrict all public API traffic to a set of CIDRs. Requests from outside the allowlist are rejected with `403 ip_not_allowed`. See [API IP allowlist](/conventions#api-ip-allowlist).
- **Workflow `send_webhook` action.** Workflow automations can now deliver their triggering event to subscribed webhooks, with optional event-type override and an optional subset of recipient webhooks. See [Workflow engine → Actions](/integrations/workflow-engine#actions).

### Updates

- **Per-stage workflow outcomes.** `GET /v1/workflows/runs/{id}` now returns the outcome of every executed step: status (`success`, `failed`, `skipped`), an optional message, the artifacts consumed and produced, and a per-step timestamp. Existing fields are unchanged. `completed_at` also now populates on canceled runs.
- **Automatic webhook delivery is live.** Subscribed webhooks now receive a fan-out delivery whenever a matching domain event occurs. Previously only the manual test endpoint dispatched a delivery. All webhooks for a single source event share an `event_id` so receivers can dedupe. See [Webhooks](/integrations/webhooks).
- **Webhook delivery history.** Inspect every delivery attempt (event fan-out, manual test, or workflow-triggered) via the new `GET /v1/webhooks/{id}/deliveries` endpoint, and review aggregate stats (`last_delivery_status`, `delivery_success_rate`, `delivery_count`) on the webhook itself. See [Webhook delivery history](/integrations/webhook-deliveries).

### Breaking changes

- **Webhook event types are now strictly validated.** Creating or updating a webhook with an event type outside the [event catalog](/integrations/webhooks#event-catalog) now returns `422 invalid_event_types`. Casing matters: use `Vendor.Created`, not `vendor.created`. Review your registered subscriptions before your next deploy.
- **Webhook URLs are SSRF-restricted.** Webhook `url` must be a public HTTPS endpoint. Non-HTTPS URLs, URLs with credentials or non-standard ports, and URLs resolving to private, loopback, link-local, or metadata addresses are rejected with `400 invalid_url`. The same check runs at delivery time (DNS-rebinding safe).

### Fixes

- **API keys revoke is idempotent.** Re-revoking an already-revoked key returns success without writing a duplicate audit row. Audit entries are only written on actual state transitions.

## 2026-05-16: Webhook event-type validation, SSRF restrictions, delivery history, and API IP allowlist

Reconciled against the `claude/webhook-ui-workflow` source branch. Two breaking changes and two additive features.

### Breaking

- **Webhook `events` is now strictly validated.** `POST /v1/webhooks` and `PATCH /v1/webhooks/{id}` reject any event type outside the supported [event catalog](/integrations/webhooks#event-catalog) with `422 invalid_event_types`. Previously the field was a free-form list of strings. Integrations that registered non-canonical values (for example, lowercase `vendor.created`) must switch to the exact catalog casing (for example, `Vendor.Created`) or their create/update calls will now fail.
- **Webhook URLs are SSRF-restricted.** A webhook `url` must be a public HTTPS endpoint. URLs that are non-HTTPS, carry credentials, use a non-standard port, or resolve to a private / loopback / link-local / metadata address (for example, `169.254.169.254`) are rejected at create/update with `400 invalid_url`. The same check is re-applied with DNS resolution at delivery time (DNS-rebinding safe); a delivery blocked this way is recorded with status `error`.

### Additive

- **Automatic event delivery is live.** Subscribed webhooks now receive a fan-out delivery whenever a matching domain event occurs (previously only the manual test endpoint dispatched a delivery). All webhooks for one source event share a single `event_id` so receivers can dedupe the fan-out.
- **Webhook delivery history.** New `GET /v1/webhooks/{id}/deliveries` endpoint (paginated, newest first) and a new [Webhook delivery history](/integrations/webhook-deliveries) page. Every attempt (event fan-out, manual test, or workflow-triggered) is recorded. The webhook object now also returns `last_delivery_status`, `delivery_success_rate`, and `delivery_count`.
- **Org-level API IP allowlist.** An org can restrict all `/v1/*` public API requests to a set of CIDRs via `api_ip_allowlist` on the org object (`POST /v1/org/{id}`). Requests from outside the allowlist get `403 ip_not_allowed`; the control fails closed. See [API conventions → API IP allowlist](/conventions#api-ip-allowlist).
- **Workflow `send_webhook` action.** Workflow automations can deliver their triggering event to subscribed webhooks, with an optional event-type override and an optional `webhook_ids` subset. See [Workflow engine → Actions](/integrations/workflow-engine#actions).
