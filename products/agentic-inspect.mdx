Inspect performs structured discovery using a headless browser. It works against two surfaces: a **vendor's** public and authenticated surface area, where it validates attestations and extracts evidence from trust centers; and **your own application tenants**, where it signs in and reads the live admin console to collect evidence for a chosen set of controls. Either way it captures screenshots and artifacts with full chain-of-custody metadata.

## What it does

<CardGroup cols={2}>
  <Card title="Trust center extraction" icon="building-shield">
    Parse vendor trust centers (Drata, Vanta, SafeBase, custom portals) to extract published controls, certifications, and evidence references.
  </Card>

  <Card title="Attestation validation" icon="circle-check">
    Convert claims into verified evidence by retrieving the vendor's published attestation pages and audit reports directly.
  </Card>

  <Card title="Chain-of-custody capture" icon="link">
    Record screenshots, source URLs, timestamps, and request metadata for every artifact so audit trails are defensible.
  </Card>

  <Card title="Authenticated discovery" icon="key">
    Sign in through Okta or Microsoft Entra SSO, a Google account, or a username and password, answering one-time codes and passkey prompts, so Inspect can reach evidence behind a login. For a gated vendor trust center, the agent fills in the access request form.
  </Card>
</CardGroup>

## Inspecting your own applications

The other half of Inspect points at the applications *you* run. Rather than asking a vendor whether MFA is enforced, Inspect signs in to the tenant and reads the answer off the admin console.

An **inspection** is one request against one target, with one control set and one purpose. Inside it, each control gets its own **control run**, so one control failing to collect evidence never stops the rest.

<CardGroup cols={3}>
  <Card title="Explore" icon="compass">
    Establish whether the evidence a control needs can be collected from this application at all. Run this first against an unfamiliar tenant.
  </Card>
  <Card title="Evaluate" icon="scale-balanced">
    Adjudicate the evidence against the control expectation and your scale. This is the run that produces a judgment.
  </Card>
  <Card title="Drift" icon="arrows-left-right">
    Compare against a compatible earlier inspection, so a setting an administrator changed since the last run surfaces as a difference.
  </Card>
</CardGroup>

Control sets come from the [Internal Controls Library](/control-library#internal-controls-library): 22 templates spanning 396 controls, covering identity, privileged access, integrations and OAuth, data handling, PII, PHI, GDPR, AI features and agents, resilience, SLA conformance, audit logging, and licensing, plus a CIS Controls v8.1 SaaS baseline.

Re-run on a cadence and **Drift** turns point-in-time evidence into continuous assurance: each comparison reports `exact`, `changed`, or an explicit reason it could not be compared, and a change is judged material, immaterial or inconclusive with a summary of what differs. A material change sends an alert to whoever requested the inspection, and an issue an Evaluate run raises becomes a finding, on the same Findings page as everything else, when you create one from it. See [Internal control monitoring](/products/internal-controls-monitoring) for how that joins up with third-party risk.

<Note>
  **Absent evidence is reported, never omitted.** An observation that could not be obtained still exists and still says why: unsupported, authentication required, forbidden, inconclusive, or failed. An application that does not sell a capability is not marked down for lacking it.
</Note>

<Warning>
  Progress and outcome are separate facts. "5 of 5 controls finished" says nothing about whether any of them passed, so read the status rather than the count.
</Warning>

## The AI Agents tab

Every application a company runs now ships its own AI agents, copilots and bots, and each one is an autonomous principal with authority inside that tenant. The **AI Agents** tab in Inspect is the one place a security team sees all of them, across every application, with what each may do and whether the application checks its actions at the moment they run.

<CardGroup cols={3}>
  <Card title="Applications" icon="grid-2">
    One row per connected application, with four posture cells read from its latest **AI Agents, Copilots & Autonomous Actions** inspection: Inventory, Authority, Attribution and Runtime authorization, each reading Met, a count of issues, or Not inspected. An application that was never inspected for agents stays in the list, because an unseen agent population is the finding.
  </Card>
  <Card title="Agents" icon="robot">
    One row per agent the inspection found: its name and the application's own id, owner, status, the identity it runs as, the actions it may take as the admin console lists them, who can reach it, and when an inspection last saw it. Opening a row shows the evidence and the five runtime authorization checks for that application, with **Create finding** on each one that failed.
  </Card>
  <Card title="Vendors" icon="building-shield">
    The vendors whose agents act on your data: those assessed with the **AI Agent Runtime Authorization** template, scored on delegation, runtime authorization, credentials, and audit and stop, and those whose applications hold agents but have not been assessed yet.
  </Card>
</CardGroup>

The tiles above the views count agents discovered, applications covered, agents that can write or send with nobody confirming, applications with no kill switch, and vendors assessed. Nothing on the tab is a separate record: it is read from the inspections and assessments already run, so it agrees with the inspection pages and the Findings page by construction. Coverbase's own agents are authorised and recorded on the [Agent Ledger](/products/agent-ledger), which the tab links to, so the three populations an auditor asks about are covered in one place. See [Agent runtime authorization](/security/agent-runtime-authorization) for what the checks mean.

## Common workflows

<AccordionGroup>
  <Accordion title="Eliminate manual vendor follow-up" defaultOpen icon="user-slash">
    Instead of emailing a vendor for proof of encryption at rest, Inspect pulls the relevant section from their SOC 2 in the trust center, captures it with chain-of-custody metadata, and attaches it to the evaluation.
  </Accordion>

  <Accordion title="Reassessment refresh" icon="arrows-rotate">
    When a reassessment collects documents automatically, the agent retrieves the vendor's trust center documents again, so an updated SOC 2 or a lapsed certification is what the new evaluation reads.
  </Accordion>

  <Accordion title="Pre-intake screening" icon="filter">
    Retrieve the vendor's trust center documents before sending a questionnaire. Controls the documents already answer are evaluated from them, and follow-up questions go to the vendor only for the gaps.
  </Accordion>
</AccordionGroup>
