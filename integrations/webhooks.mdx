Webhooks are the outbound half of an integration. This page documents the delivery format, how to verify signatures, retry behavior, and the event catalog. To register, list, update, delete, or test a subscription, see the [Webhooks API](/integrations/api-reference/webhooks).

<Warning>
  **Automatic event delivery is not yet wired up in the platform.** You can register webhook subscriptions and trigger a manual [test delivery](/integrations/api-reference/webhooks#test-a-webhook), and the delivery format below is exactly what a receiver will get. However, in the current codebase there is no path that automatically fans domain events (e.g. `Vendor.Created`) out to subscribed endpoints — only the test endpoint dispatches a delivery. Do not build production logic that depends on automatic event delivery without confirming availability with Coverbase. This is tracked as an open question; see the [Changelog](/changelog).
</Warning>

## Delivery format

A delivery is an HTTP `POST` with a JSON body in this exact envelope:

```json
{
  "event_id": "cbevt_test_8b3c1a4d9e7f2c5b6a8d1e3f9c7b4a2e",
  "event_type": "Assessment.Created",
  "occurred_at": 1746576120,
  "data": { "test": true }
}
```

| Field | Type | Notes |
| ----- | ---- | ----- |
| `event_id` | string | Unique delivery/event identifier. |
| `event_type` | string | The event type string. |
| `occurred_at` | integer | Unix timestamp in **seconds** at delivery time. |
| `data` | object | Event-specific payload. For test deliveries this is `{"test": true}`. |

There is no top-level `workflow_run_id` and no other top-level fields — the envelope is exactly the four keys above.

### Request headers

| Header | Value |
| ------ | ----- |
| `Content-Type` | `application/json` |
| `Coverbase-Signature` | Lowercase hex HMAC-SHA256 of the raw request body, keyed by your webhook `secret`. |
| `X-Coverbase-Event-Id` | Same value as `event_id`. |
| `X-Coverbase-Event-Type` | Same value as `event_type`. |

## Signature verification

The signature is `HMAC-SHA256(secret, raw_request_body)` rendered as a lowercase hex string, sent in the `Coverbase-Signature` header. Verify it against the **raw bytes** of the request body before parsing JSON.

```python Python
import hashlib
import hmac

def verify(raw_body: bytes, signature_header: str, secret: str) -> bool:
    expected = hmac.new(secret.encode(), raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature_header)

# Flask example
from flask import Flask, request, abort

app = Flask(__name__)
WEBHOOK_SECRET = "whsec_a1b2c3d4e5f6a7b8c9d0e1f2"  # the secret you registered

@app.post("/coverbase")
def receive():
    raw = request.get_data()  # raw bytes, do not re-serialize
    sig = request.headers.get("Coverbase-Signature", "")
    if not verify(raw, sig, WEBHOOK_SECRET):
        abort(401)
    event = request.get_json()
    # handle event["event_type"] / event["data"]
    return "", 200
```

```javascript Node.js
const crypto = require("crypto");

function verify(rawBody, signatureHeader, secret) {
  const expected = crypto
    .createHmac("sha256", secret)
    .update(rawBody)
    .digest("hex");
  return crypto.timingSafeEqual(
    Buffer.from(expected),
    Buffer.from(signatureHeader),
  );
}

// Express example (use express.raw so rawBody is the unparsed buffer)
app.post(
  "/coverbase",
  express.raw({ type: "application/json" }),
  (req, res) => {
    const sig = req.header("Coverbase-Signature") || "";
    if (!verify(req.body, sig, process.env.WEBHOOK_SECRET)) {
      return res.status(401).end();
    }
    const event = JSON.parse(req.body.toString("utf8"));
    // handle event.event_type / event.data
    res.status(200).end();
  },
);
```

## Delivery & retries

| Property | Value |
| -------- | ----- |
| HTTP method | `POST` |
| Connection timeout | 10 seconds per attempt |
| Retries | Up to 5 attempts on failure (timeout or connection error) |
| Endpoint requirement | HTTPS only |

There is no published exponential-backoff schedule or extended (multi-hour) retry window — retries are bounded at 5 attempts. Receivers should treat the same `event_id` as potentially delivered more than once and process idempotently. Respond with a `2xx` quickly to acknowledge.

## Event catalog

The following event types have backend emission implemented (the platform's `SupportedEventType` set). Use these exact, case-sensitive strings in a subscription's `events` array:

| Event type |
| ---------- |
| `Assessment.Created` |
| `Assessment.AssigneeChanged` |
| `Assessment.StatusChanged` |
| `IntakeSession.Created` |
| `IntakeSession.Submitted` |
| `Service.Created` |
| `Service.Updated` |
| `OrgIntake.Disabled` |
| `OrgIntake.QuestionnaireRemoved` |
| `QuestionnaireResponse.Created` |
| `QuestionnaireResponse.StatusChanged` |
| `Review.StatusChanged` |
| `Procurement.Created` |
| `Procurement.StatusChanged` |
| `Vendor.Created` |
| `Vendor.Updated` |
| `WorkQueueItem.Created` |
| `WorkQueueItem.Completed` |

Workflow lifecycle event strings (`Workflow.Checkpoint`, `Workflow.Completed`, `Workflow.Failed`) are defined in the platform's event enum and reserved for workflow-run correlation, but they are not part of the emission-backed `SupportedEventType` set above.

<Note>
  The `events` field on a subscription is a free list of strings — it is **not** rejected if it contains a value outside this catalog. Subscribing to a value that is never emitted simply results in no deliveries. Stick to the exact strings above.
</Note>
