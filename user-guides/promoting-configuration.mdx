Promotion copies configuration, not records. The mistake people make most often is expecting vendors, assessments or findings from the sandbox to arrive in production. They never do.

## Before you start

- **Start from the sandbox.** Promotion is available only in an organization whose status is **Sandbox**. The left navigation shows a **Sandbox** badge when you are in one.
- **Be an Admin in both organizations.** You need the Admin role in the sandbox and in the organization you promote to. Members of the sandbox cannot promote, whatever their role in the destination.
- **Production or another sandbox.** You can promote to an active production organization or to another sandbox, so a change can move from a development sandbox to a test sandbox and then to production. Proof of concept and inactive organizations cannot receive a promotion.
- **A second person approves.** Someone in the destination other than you, with permission to change organization settings, approves the package before it is applied.

## Promote your configuration

<Steps>
  <Step title="Open Promote configuration">
    In the sandbox, go to **Configuration → Organization → Promote configuration**.
  </Step>
  <Step title="Choose the destination">
    Pick the destination organization in **Promote to**. Organizations you cannot promote to are listed with the reason, such as **You need to be an admin there**.
  </Step>
  <Step title="Review the changes">
    Coverbase compares the two organizations and lists every area that differs, with how many items are **new** and how many are **updated**. Expand an area to see each item. An updated item shows each changed value, with the current production value struck through and the sandbox value beside it.
  </Step>
  <Step title="Choose what to include">
    Every area with changes is included by default. Clear the checkbox on an area to leave it out of this promotion. You can promote it later.
  </Step>
  <Step title="Send the package">
    Select **Promote** and check the summary in the confirmation. Give the **Package Name** and select **Promote to** the destination. Coverbase saves the reviewed changes as the destination's next package version and shows **Package sent to** the destination **for approval**. Nothing changes in the destination yet.
  </Step>
</Steps>

## Approve, apply and roll back a package

Packages are listed on **Configuration → Organization → Promote configuration** in both organizations: **Packages Sent From This Sandbox** in the sandbox, and **Packages for This Organization** in the destination. Each row shows the **Package** name and version (for example "Q4 methodology · v3"), its **Status**, **From**, **To**, **Requested By**, **Reviewed By** and when it was **Applied**. **View changes** opens the changes the requester reviewed.

<Steps>
  <Step title="Approve or reject">
    In the destination, a person other than the requester clicks **Approve** or **Reject**, with an optional **Note**. The status moves from **Waiting for approval** to **Approved** or **Rejected**. The requester cannot review their own package.
  </Step>
  <Step title="Apply">
    Click **Apply** on an approved package and confirm. Its changes take effect in the destination now, and the status is **Applied**. If either organization changed since the package was reviewed, Coverbase refuses the apply, so what lands is what both people saw.
  </Step>
  <Step title="Roll back if needed">
    Click **Roll back** on an applied package and confirm. Settings it changed go back to what they were before it was applied, and anything it added is archived. The status is **Rolled back**. Coverbase refuses a rollback when anything the package changed was edited after it was applied.
  </Step>
</Steps>

Neither applying nor rolling back deletes anything that existed before the package. Each apply and rollback is listed under **Past promotions** with who ran it, when, and how many items it changed in each area.

## What a promotion carries

Items are matched by name, not by internal ID, because the two organizations never share IDs. An item with the same name in both is compared field by field. An item only in the sandbox is added.

| Area | Matched on | What is copied | Notes |
| --- | --- | --- | --- |
| Organization settings | The setting | Assessment and risk scoring settings, reassessment timing, reviewer and completion rules, onboarding and W-9 reminders, the central portal switch | |
| Terminology | The default term | Your renamed terms, such as **Vendor** to **Supplier** | Terms production renamed and the sandbox did not are kept |
| Statuses | Record type and name | Name, color, icon, description, group and whether it is on the standard path | The default status in production does not change |
| Tags | Key and value | Color | |
| Custom fields | Field name | Field settings, options, whether it is turned on, which records it appears on, and its section | Values on records are not copied. A field archived in production is restored. A missing section is created |
| Risk domains | Name | Description and weight | |
| Approval options | Name | Color and icon | |
| Email layouts | Layout type | Template, brand logo and color, font and footer | |
| Control sets | Name | The control set with its sections, controls, scales, conditions and significant-deficiency floors | An updated control set replaces the production version. If an assessment already uses the old version, it stays available to that assessment |
| Radar detectors | Name | Instructions, type, settings, severity threshold, categories, outreach and risk impact, sources and vendor tag filters | New detectors arrive turned off. Turn them on in Radar when you're ready. A detector that filters on a tag production lacks needs **Tags** included in the same promotion |

Promotion never deletes anything in production. Settings production has that the sandbox lacks are kept. An updated control set archives the version it replaces.

### What is not copied

- **Records.** Vendors, services, assessments, findings, contracts, engagements and every other record stay where they are.
- **People and access.** Members, user groups, roles and single sign-on are managed in each organization. With [SCIM provisioning](/security/identity-and-access#lifecycle-management), your identity provider provisions each organization separately.
- **Vendor-specific scoping on detectors.** A detector limited to named vendors arrives without that list, because those vendors exist only in the sandbox. The review marks these detectors.
- **Radar sources.** A detector that reads from a source production does not have is marked **Some of its Radar sources aren't set up there**. Set the source up in production, then promote again.
- **Integrations, API keys, webhooks and secrets.** Credentials never leave the organization they were created in.

## If something changes while you review

The review is a snapshot. If anyone changes either organization between your review and sending the package, Coverbase refuses it and shows **Something changed since you reviewed it**. The same check runs again when the package is applied. The review reloads with the current differences. Check them and promote again. Nothing is written until the review you confirm matches both organizations.

## Troubleshooting

| What you are seeing | What is happening |
| --- | --- |
| **Promote configuration** is not in Configuration | You are not in a sandbox organization, or you are not an Admin. Switch to your sandbox |
| The page says promotion starts from a sandbox | The organization you are in is not a sandbox. Switch organizations from the top of the left navigation |
| Your destination is listed but cannot be chosen | You are not an Admin there, or it is a proof of concept or inactive organization. The reason is shown under its name |
| Your production organization is not listed | You are not a member of it. Ask one of its Admins to add you |
| A detector shows as updated again after promoting | It reads from a Radar source production does not have. Set the source up in production |
| **Approve** is refused | You sent the package. Someone else in the destination approves it |
| **Roll back** is refused | Something the package changed was edited after it was applied. Change it back by hand, or send a new package |
| Nothing changed in the destination after you promoted | The package waits for someone in the destination to approve and apply it |
| The promotion was refused | Something changed in either organization after you reviewed. Review the updated changes and promote again |
| The promotion was refused and names a detector and a tag | The detector filters on a tag production does not have. Include **Tags**, or create the tag in production, and promote again |
| The promotion was refused and names a custom field | The field cannot change that way, for example a serial ID field changing its type or starting number. Change it back in the sandbox, or leave **Custom fields** out |
| A control set appears twice in production | One is archived, or kept for assessments that started on the earlier version. Later promotions update the newer one |
