**Radar** is Coverbase's continuous third-party monitoring surface. These object types are exposed here:

- A **radar event** (`cbrevent_...`) records something that happened to one or more vendors and groups the source data behind it (news, advisories, breach disclosures).
- A **radar alert** (`cbrdrres_...`) is one detector's verdict that a piece of source data is relevant to one vendor. Alerts are what you triage here: dismiss the noise, or escalate into a [reassessment](/api-reference/reassessments).

- A **signal** (`cbrag_...`) is one radar event as it affects your organization. It rolls up the event's alerts into one row with your organization's status, title, and summary. You can list, dismiss, restore, and acknowledge signals, and move them between your organization's statuses.
- A **case** (`cbcase_...`) tracks one incident across the vendors it may affect. Each vendor on a case has a **case thread** (`cbcseth_...`) that records whether that vendor was affected and what was done about it.

- A **source** (`cbradarsrc_...`) is something Radar watches for your organization: a website, an RSS feed, an API, or a snapshot of a page or list. Each source reads an **origin**, the URL Radar pulls. An origin is private to your organization or shared from the Coverbase source library.
- A **detector** (`cbrdrdet_...`) decides which events matter to which vendors. You can create and tune detectors, back-test them against past events, and teach them with **examples** of events they should and should not alert on.

Read the event for what happened, the signal for where your organization stands on it, and the alerts for which detector flagged which vendor. See the Supplier Radar [key concepts](/products/supplier-radar#key-concepts).

All endpoints are org-scoped to the API key. See [API conventions](/conventions) for shared behavior, including [pagination](/conventions#pagination).

The read routes need the `radar_alert:read:org` permission, and the routes that change something need `radar_alert:update:org`. API keys hold both. You cannot archive a case or a case thread through the API.

The source and detector routes use the Radar detector permissions instead: reads need `radar_detector:read:org`, creating a detector needs `radar_detector:create:org`, and edits, back-tests and examples need `radar_detector:update:org`. Pulling a source needs `radar_detector:run:org`, and saving Black Kite settings needs `integration:update:org`. API keys hold all of them. An API key cannot archive or restore a source or a detector, or delete an example: those requests return `403 api_key_not_allowed`, and a signed-in user must make them.

## Create a radar event

<ParamField path="method" type="POST">
  `POST /v1/radar/events`
</ParamField>

Returns `201 Created`. Use this to seed an event into Radar without waiting for a source feed to pick up the underlying article; useful for recording out-of-band incidents and for exercising your detectors against a known event. Supplied vendors are linked to the event as **primary-impacted**, and the event is evaluated against your detectors unless you opt out (see [detector evaluation](#detector-evaluation)).

### Request body

<ParamField body="name" type="string" required>
  Short event name.
</ParamField>

<ParamField body="summary" type="string" required>
  Event summary / description.
</ParamField>

<ParamField body="primary_impact_type" type="string" required>
  Primary impact category. Case-sensitive; one of `Infosec`, `Financial`, `Operational`, `Legal`, `Compliance`, `Reputational`, `Contractual`, `ESG`, `Corporate`, `Geopolitical & External`, `Inapplicable`, `Other`.
</ParamField>

<ParamField body="secondary_impact_types" type="string[]">
  Additional impact categories, from the same list as `primary_impact_type`. A
  value outside it is rejected with `422`. These categories decide which
  category-filtered detectors can match the event.
</ParamField>

<ParamField body="vendor_ids" type="string[]">
  Vendors directly impacted (`cbvndr_...`). Each is linked as primary-impacted. Vendors that cannot be resolved, or that are not yet linked to a company record, are skipped silently.
</ParamField>

<ParamField body="risk_domain_ids" type="string[]">
  Risk domains to record on the event (`cbrdom_...`), returned on the [radar
  event object](#radar-event-object). An id your org does not have is rejected
  with `400 risk_domain_not_found`.
</ParamField>

<ParamField body="source_url" type="string">
  URL of the underlying article / report.
</ParamField>

<ParamField body="source_name" type="string">
  Name of the source.
</ParamField>

<ParamField body="occurred_at" type="integer">
  When the event occurred (Unix seconds). Defaults to now when omitted.
</ParamField>

<ParamField body="create_alert" type="boolean">
  Evaluate the event against the detectors that target each linked vendor, raising
  [radar alerts](#list-radar-alerts) for the ones that fire. Default `true`. Pass
  `false` to record an event without spending a model call per (detector, vendor).
</ParamField>

### Detector evaluation

The scheduled Radar pipeline is source-driven: it evaluates what its configured
sources pull in, and never sees an event created through this endpoint. Events
posted here are therefore evaluated out of band, which happens by default. Pass
`create_alert: false` to store one without evaluating it.

Evaluation is asynchronous: the response returns as soon as the event is stored,
and alerts appear on [`GET /v1/radar/alerts`](#list-radar-alerts) once the detectors
finish, each carrying this event's `event_id`. What runs against the event:

- **Vendors.** The vendors in `vendor_ids` that resolve within your org, plus the
  vendors that depend on them: a breach at a supplier is evaluated against the
  customers exposed to it, the same expansion the scheduled pipeline performs, and
  through the same caps. An event with no resolvable vendor is stored but never
  evaluated.
- **Detectors.** Only the ones that already target each of those vendors, including
  the detector's source scoping: a detector limited to specific sources sees this
  event only if it includes the org's **Manually-created events** source. Detectors
  with an impact-category filter are matched against the event's own
  `primary_impact_type` and `secondary_impact_types`.
- **Cost.** One model call per (detector, vendor) pair, counting the vendors
  reached by expansion. Pass `create_alert: false` on events you only want recorded.

Re-posting the same event is safe: each (event, vendor, detector) combination is
evaluated once, so retries do not duplicate alerts or re-notify reviewers.

To tell whether an event was evaluated, read [its alerts](#list-an-events-alerts):
`evaluation_status` separates "never evaluated", "still evaluating", and "evaluated
with nothing raised".

### Example request

```bash cURL
curl -X POST "https://api.coverbase.app/v1/radar/events" \
  -H "Authorization: Bearer ak_live_xxx" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Acme data breach",
    "summary": "Acme disclosed unauthorized access to a customer database.",
    "primary_impact_type": "Infosec",
    "vendor_ids": ["cbvndr_e448ba62882143f3ba0c140bb2e30162"],
    "source_url": "https://news.example.com/acme-breach",
    "source_name": "Example News",
    "create_alert": true
  }'
```

Returns the [radar event object](#radar-event-object).

## List an event's alerts

<ParamField path="method" type="GET">
  `GET /v1/radar/events/{event_id}/alerts`
</ParamField>

Returns the detector results for one event, plus the state of its evaluation. An
event that raised nothing looks the same from outside whether it was never
evaluated, is still being evaluated, or was evaluated and judged irrelevant; the
envelope's counts separate the three.

<ParamField query="include_non_alerting" type="boolean">
  Include detector runs that scored the event without alerting. Default `false`.
</ParamField>

<ParamField query="is_dismissed" type="boolean">
  Dismissal filter. Omit for both; `true` for only dismissed; `false` for only active.
</ParamField>

<ParamField query="include_archived" type="boolean">
  Include archived results. Default `false`.
</ParamField>

<ParamField query="limit" type="integer">
  Page size. Default `50`, range `1`-`200`.
</ParamField>

<ParamField query="offset" type="integer">
  Page offset. Default `0`.
</ParamField>

The response is the usual list envelope of [radar alert objects](#radar-alert-object)
(`items`, `total`, `limit`, `offset`) plus:

<ResponseField name="evaluation_status" type="string">
  `not_requested` (the event was stored without evaluation, or no linked vendor
  resolved), `pending` (evaluation was requested and no detector has reported yet),
  or `completed` (at least one detector scored the event).
</ResponseField>
<ResponseField name="evaluated_count" type="integer">Detector results recorded for the event, alerting or not, ignoring your filters.</ResponseField>
<ResponseField name="alert_count" type="integer">How many of those results raised an alert.</ResponseField>

Returns `404 radar_event_not_found` for an unknown event.

## Dismiss a radar alert

<ParamField path="method" type="POST">
  `POST /v1/radar/alerts/{alert_id}/dismiss`
</ParamField>

Marks an alert as dismissed (triaged as not actionable). Returns the refreshed [radar alert object](#radar-alert-object).

### Request body

<ParamField body="reason" type="string">
  Optional dismissal reason. It shows in the dashboard and goes into the detector's learning context. Each person you mention in it with `@[name](cbuser_...)` gets a notification.
</ParamField>

<ParamField body="suppress_similar" type="boolean">
  Accepted for compatibility. When the alert belongs to an event, every dismissal records it as a negative example on its detector, so future runs suppress similar alerts, whatever this field says.
</ParamField>

### Example request

```bash cURL
curl -X POST "https://api.coverbase.app/v1/radar/alerts/cbrdrres_9a8b7c6d5e4f3a2b1c0d9e8f7a6b5c4d/dismiss" \
  -H "Authorization: Bearer ak_live_xxx" \
  -H "Content-Type: application/json" \
  -d '{ "reason": "Duplicate of an existing event", "suppress_similar": true }'
```

| Status | Body | When |
| ------ | ---- | ---- |
| 404 | `{"detail": {"code": "alert_not_found", "message": "Radar alert not found."}}` | Not found, or not in the API key's org. |

Dismissing an already-dismissed alert is a no-op that returns `200` with the alert; a
`reason` supplied on the repeat call replaces the stored one.

## Diagnose an event

</ParamField>

## Update a detector

<ParamField path="method" type="PATCH">
  `PATCH /v1/radar/detectors/{detector_id}`
</ParamField>

Changes the fields you send and returns the [detector object](#detector-object). It takes the create fields except `library_slug` and `attach_library_sources`, plus these:

<ParamField body="add_default_reviewer_user_ids" type="string[]">
  Users to add as reviewers, keeping the current ones.
</ParamField>

<ParamField body="add_default_reviewer_group_ids" type="string[]">
  Groups to add as reviewers, keeping the current ones.
</ParamField>

<ParamField body="severity_threshold" type="string">
  Also accepts `NO_THRESHOLD`, which needs `instructions`.
</ParamField>

<ParamField body="risk_impact_config" type="object | null">
  Send `null` to remove it.
</ParamField>

<ParamField body="outreach_config" type="object | null">
  When Coverbase AI may email vendors about this detector's alerts: `enabled`, `min_severity`, `vendor_tiers`, and `follow_up_days`. Send `null` to turn outreach off. It applies only where vendor outreach is available.
</ParamField>

<ParamField body="is_archived" type="boolean">
  Archive or restore the detector. API keys get `403 api_key_not_allowed`.
</ParamField>

## List a vendor's detectors

<ParamField path="method" type="GET">
  `GET /v1/radar/vendors/{vendor_id}/detectors`
</ParamField>

Lists the detectors that monitor one vendor, by their tag, include, and exclude rules, with the fields of a [listed detector](#list-detectors). Pass `include_disabled=true` to also list detectors that are off. Pages with `limit` and `offset`. Returns `404 vendor_not_found` for an unknown vendor.

## Suggest risk domains

<ParamField path="method" type="POST">
  `POST /v1/radar/detectors/suggest-risk-domains`
</ParamField>

Returns `risk_domain_ids`: your organization's risk domains that match a detector configuration. Nothing is saved. To use them, send them as `risk_domain_ids` when you create or update the detector. The body takes `name` (required), `description`, `instructions`, and `category_filters`.

## Suggest instructions

<ParamField path="method" type="POST">
  `POST /v1/radar/detectors/{detector_id}/suggest-instructions`
</ParamField>

Drafts new instructions from the detector's examples and returns `current_instructions`, `suggested_instructions`, and `rationale`. Nothing is saved. `suggested_instructions` is `null` when the detector has no examples yet. To use the draft, send it as `instructions` in [update a detector](#update-a-detector).

## Back-test a detector

<ParamField path="method" type="POST">
  `POST /v1/radar/detectors/{detector_id}/tests`
</ParamField>

Returns `202 Accepted` with a `test_run_id`. Radar runs the detector against the events created between `created_at_from` and `created_at_to` (Unix seconds) in the background, up to `max_events` (default `50`, range `1` to `200`). A back-test creates no alerts.

## Read back-test results

<ParamField path="method" type="GET">
  `GET /v1/radar/detectors/{detector_id}/tests/{test_run_id}`
</ParamField>

Returns `is_complete` and the `items` found so far. Each item has `id`, `vendor_id`, `event_id`, `event_created_at`, `should_alert`, `severity`, `summary`, `already_alerted`, and `created_at`. `already_alerted` is `true` when the detector already raised an alert for that vendor and event.

## Create alerts from a back-test

<ParamField path="method" type="POST">
  `POST /v1/radar/detectors/{detector_id}/tests/{test_run_id}/alerts`
</ParamField>

Turns the results in `result_ids` into real alerts and notifies the detector's default reviewers. Returns `alert_ids` and `skipped_already_alerted`, the number of results skipped because the detector already alerted on them. A result from another detector or run returns `400 result_not_in_test_run`.

## Teach a detector from a back-test

<ParamField path="method" type="POST">
  `POST /v1/radar/detectors/{detector_id}/tests/{test_run_id}/teach`
</ParamField>

Adds the event of each result in `should_alert_result_ids` as a positive example, and each in `should_not_alert_result_ids` as a negative one. Labelling an event again moves it to the other side. Returns `applied_count`, `positive_example_count`, and `negative_example_count`. A result from another detector or run returns `400 result_not_in_test_run`.

## Dismissal example object

An example is an event a detector should (`positive`) or should not (`negative`) alert on. It has `id`, `detector_id`, `kind`, `event_id`, `alert_id`, `example_summary`, `reason`, `dismiss_code`, `created_at`, and `updated_at`. Coverbase classifies the reason on a new negative example and fills in `dismiss_code`.

## List a detector's examples

<ParamField path="method" type="GET">
  `GET /v1/radar/detectors/{detector_id}/dismissal-examples`
</ParamField>

Lists the detector's examples, newest first. Filter with `kind` (`negative` or `positive`); pages with `limit` and `offset`.

## Add an example

<ParamField path="method" type="POST">
  `POST /v1/radar/detectors/{detector_id}/dismissal-examples`
</ParamField>

Returns `201 Created` with the [example](#dismissal-example-object). The body takes `event_id` and `example_summary` (both required), `kind` (default `negative`), `reason`, and `alert_id`. An event your organization cannot see returns `404 event_not_found`.

## Update an example

<ParamField path="method" type="PATCH">
  `PATCH /v1/radar/dismissal-examples/{example_id}`
</ParamField>

Replaces the example's `reason` and returns the [example](#dismissal-example-object). Send `null` to clear it. Returns `404 dismissal_example_not_found` for an unknown example.

## Delete an example

<ParamField path="method" type="DELETE">
  `DELETE /v1/radar/dismissal-examples/{example_id}`
</ParamField>

Returns `204 No Content`. API keys get `403 api_key_not_allowed`, so a signed-in user must delete examples.
