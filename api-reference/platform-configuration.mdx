These endpoints let you manage your organization's configuration: the **status** options each record type moves through, **custom field sections**, **email templates**, **workflow definitions**, **Coverbase AI agents** and their **preferences**, **reports**, and the **TPRM lifecycle configuration** that names your TPRM Office and decides who past-due vendor reminders copy.

All endpoints are org-scoped to the API key. See [API conventions](/conventions) for shared behavior. For custom fields, see the [Custom fields API](/api-reference/custom-fields). For workflows, see the [Workflows API](/api-reference/workflows).

<Note>
An organization API key can read roles, email templates and reports, and export reports. It does not hold the `org_settings` permissions, `email_template` write permissions, `report` create, update or archive permissions, `role` write permissions or `billing:read:org`. In an organization that enforces roles, call the routes that need them with a key created by a person whose role holds the permission.
</Note>

None of these honor `Idempotency-Key`. An API key cannot archive a status, custom field section, email template, workflow, rule, report or agent preference. To archive one, use Coverbase. Every list endpoint takes `limit` (1 to 500, default 100) and `offset` (default 0) and returns `items`, `total`, `limit` and `offset`.

## Statuses

A **status** (`cbstatus_...`) is one option a record type can be in, for example a finding's "Awaiting vendor". Each record type has its own ordered list. Every status belongs to one of four groups: `unstarted`, `started`, `completed` or `canceled`.

The `target_type` names the record type. It is one of `assessment`, `procurement`, `engagement`, `vendor`, `service`, `contract_review`, `procurement_review`, `assessment_review`, `assessment_risk_domain_review`, `radar_signal_review`, `finding`, `rfp`, `contract`, `radar_event` or `dark_web_exposure`.

The `color` is one of `gray`, `green`, `red`, `yellow`, `blue`, `plum`, `orange`, `purple`, `brown` or `pink`. The `icon` is one of `circle`, `progress`, `check`, `subtract`, `close`, `flag`, `survey`, `question`, `clock` or `eye`.

### List statuses

<ParamField path="method" type="GET">
  `GET /v1/statuses`
</ParamField>

Returns the statuses for one record type in display order.

<ParamField query="target_type" type="string" required>
  The record type to list statuses for.
</ParamField>

<ParamField query="include_archived" type="boolean" default="false">
  Set to `true` to include archived statuses.
</ParamField>

<ParamField query="limit" type="integer" default="100">
  Maximum number of statuses to return, from 1 to 500.
</ParamField>

<ParamField query="offset" type="integer" default="0">
  Number of statuses to skip.
</ParamField>

```bash cURL
curl "https://api.coverbase.app/v1/statuses?target_type=finding" \
  -H "Authorization: Bearer ak_live_xxx"
```

The response has `items` (an array of [status objects](#status-object)), `total`, `limit` and `offset`.

### Create a status

<ParamField path="method" type="POST">
  `POST /v1/statuses`
</ParamField>

Returns `201 Created` with the new [status object](#status-object). The new status goes to the end of the list unless you pass `sort_order`.

<ParamField body="target_type" type="string" required>
  The record type the status belongs to.
</ParamField>

<ParamField body="label" type="string" required>
  The name people see.
</ParamField>

<ParamField body="color" type="string" required>
  The status color.
</ParamField>

<ParamField body="icon" type="string" required>
  The status icon.
</ParamField>

<ParamField body="description" type="string" default="&quot;&quot;">
  What the status means.
</ParamField>

<ParamField body="group" type="string" default="unstarted">
  `unstarted`, `started`, `completed` or `canceled`.
</ParamField>

<ParamField body="sort_order" type="string">
  A fractional order key. Copy one from a listed status to place the new status next to it.
</ParamField>

<ParamField body="is_default" type="boolean" default="false">
  Set to `true` to make this the status new records start in.
</ParamField>

<ParamField body="on_standard_path" type="boolean" default="true">
  Whether the status is part of the normal progression.
</ParamField>

<ParamField body="metadata" type="object">
  Settings specific to the record type.
</ParamField>

```bash cURL
curl -X POST "https://api.coverbase.app/v1/statuses" \
  -H "Authorization: Bearer ak_live_xxx" \
  -H "Content-Type: application/json" \
  -d '{
    "target_type": "finding",
    "label": "Awaiting vendor",
    "color": "yellow",
    "icon": "progress",
    "group": "started"
  }'
```

## TPRM lifecycle configuration

The TPRM lifecycle configuration names the user group that acts as your TPRM Office and decides who past-due vendor reminders copy. These endpoints return `404` when the TPRM lifecycle is not enabled for your organization.

### Get the configuration

<ParamField path="method" type="GET">

## Reminder rules

A **rule** sends a contract or document reminder. It has a `rule_name` (for example `contract_notification`), a trigger (`trigger_config` and `trigger_value`, for example `days_before_contract_end` with `{"days": [30, 60]}`), an optional condition (`condition_config` and `condition_value`), and a command (`command_config` and `command_value`, for example `send_contract_reminder` with `{"emails": ["admin@company.com"]}`).

`GET /v1/rules` lists your rules. Pass `include_archived=true` to include archived ones.

To create a rule, send `POST /v1/rules` with every field above except the optional condition. Coverbase checks each value against its configuration type and returns `422 invalid_rule` when one does not fit.

To change a rule, send `PATCH /v1/rules/{rule_id}` with the fields to change. A value applies only when you also send its configuration type, for example `trigger_value` with `trigger_config`. The request is refused with `422` if it contains `is_archived`.

## Coverbase AI agents and preferences

These endpoints return `404 not_enabled` when Coverbase Agent is not enabled for your organization.

An **agent** runs Coverbase AI playbooks on a schedule or a trigger. `GET /v1/agents` lists your agents, oldest first. Each item has `id`, `name`, `instructions`, `playbooks`, `schedule_cron`, `timezone`, `enabled`, `paused`, `created_at` and `updated_at`. The response also has `agents_paused`, which is `true` when every agent in your organization is paused.

`GET /v1/agent-templates` lists ready-made agents: `key`, `name`, `description`, `schedule_cron` and `playbooks`. `agent_id` is set when your organization already made an agent from the template. To make one, send `POST /v1/agents/from-template` with `template_key` and an optional `timezone` (default `UTC`). The new agent starts turned off.

To pause or resume every agent at once, send `PUT /v1/agents/paused` with `paused` set to `true` or `false`. The response has `agents_paused`.

To stop an agent from starting runs, send `POST /v1/agents/{agent_id}/pause`. Its live runs stop at their next turn. To let it start runs again, send `POST /v1/agents/{agent_id}/resume`. Both return the agent.

A **preference** is a standing instruction every Coverbase AI run reads. `GET /v1/agent-preferences` lists them, oldest first. Each item has `id`, `text`, `source`, `playbook`, `enabled`, `created_at` and `updated_at`.

To add a preference, send `POST /v1/agent-preferences` with `text` and an optional `playbook`. A preference without a playbook applies to every playbook. To change one, send `PATCH /v1/agent-preferences/{preference_id}` with any of `text`, `enabled` and `playbook`. Send `playbook: null` to apply it to every playbook again.

### Tool policies

`GET /v1/agent-tool-policies` lists every Coverbase AI tool that changes data. Each item has `tool`, `label`, `effect`, `policy` and `locked`. A policy is `auto` (runs without asking when a run is set to not stop), `ask` (always asks) or `off` (refused). A `locked` tool always asks.

To change policies, send `PATCH /v1/agent-tool-policies` with `policies`, an object of tool name to policy. Tools you leave out keep theirs. An unknown or locked tool returns `422 invalid_tool_policy`.

## Custom document types and AI prompts

`PATCH /v1/custom-document-types/{custom_document_type_id}` renames, regroups or redescribes one of your document types with `name`, `description` and `classification`. A new description runs the detection check again. A name another type already uses returns `409 document_type_name_taken`.

### Create a custom document type from example files

The draft, create and add-examples endpoints take `multipart/form-data`. Send each example file as its own `files` field, from 1 to 10 per request. Each file follows the same type and size limits as a vendor document upload, and a file outside them returns `400` or `413` before anything is stored.

1. `POST /v1/custom-document-types/draft` with `name` and `files` returns a suggested `description`, `classification` and `confusable_document_types`, plus `existing_document_type` when your examples already match a built-in type and `unreadable_examples` for files with no readable text. Nothing is saved.
2. `POST /v1/custom-document-types` with `name`, `description`, `classification`, up to 3 `confusable_document_types` fields and `files` creates the type, returns `201` and starts its detection check. A name another type already uses returns `409 document_type_name_taken`.
3. `POST /v1/custom-document-types/{custom_document_type_id}/examples` with `files` adds examples and runs the check again. A type holds at most 10 examples; more returns `422 too_many_examples`.

```bash
curl -X POST "$BASE_URL/v1/custom-document-types" \
  -H "Authorization: Bearer $API_KEY" \
  -F "name=Modern Slavery Statement" \
  -F "description=Annual statement under the UK Modern Slavery Act." \
  -F "classification=esg" \
  -F "files=@statement-2024.pdf" \
  -F "files=@statement-2025.pdf"
```

The detection check can pull in vendor documents that look like your new type. Settle each one with `POST /v1/custom-document-types/{custom_document_type_id}/lookalikes/{vendor_document_id}/decision` and a `decision` of `keep`, which leaves the document's type, or `relabel`, which moves it to your type. A document the check did not pull in returns `404 lookalike_not_found`.

### AI prompts

`GET /v1/prompts/{prompt_name}/versions` lists your saved versions of one AI prompt, for example `finding_creation`, with `is_selected` on the version in use. `PUT /v1/prompts/{prompt_name}` saves a new version with `prompt_text` and an optional `prompt_key` and uses it. `POST /v1/prompts/{prompt_name}/select` uses an earlier `version_num`. The organization's assessment summary returns `409 use_summary_instructions`; manage it with the summary instructions endpoints.

`PATCH /v1/prompts/{prompt_name}/versions/{version_num}` renames a version with `name`, or archives it or brings it back with `is_archived`. When you archive the version in use, Coverbase uses `new_selected_version_num`, or your newest unarchived version when you leave it out. Archiving and unarchiving need a user key: an API key gets `403 api_key_not_allowed`. An unknown version returns `404 prompt_version_not_found`.

## Coverbase AI runs

A **run** is one instruction Coverbase AI carries out, such as "Onboard Figma for design collaboration". A run belongs to whoever started it. With an API key, that is the key, so each key sees only its own runs. Every route here returns `404 not_enabled` when Coverbase AI is off for your organization.

`GET /v1/agent-playbooks` lists the jobs Coverbase AI knows how to do. Each item has `playbook`, `title`, `description`, `steps` and an `example` instruction that starts it. `GET /v1/agent-setup` returns each setup step with `done`, the `instruction` that starts the guided setup, and `complete`.

### Start and follow a run

To start a run, send `POST /v1/agent-runs` with `instruction`. Optional fields are `mode` (`background`, the default, or `guided`) and `approval_policy` (`ask`, the default, or `auto`). Coverbase returns `201 Created` with the run. The run works in the background and stops before any change it proposes, so a person can accept or reject it. An API key cannot start a run with `approval_policy: auto`, because that run approves its own changes.

`GET /v1/agent-runs` lists your runs, newest first. Filter with `active`, `archived`, `search` and `status` (repeat it for several), and page with `limit` (1 to 50, default 20) and `offset`. `GET /v1/agent-runs/{run_id}` returns one run with its `status`, `plan`, `needs_you`, `report` and `error`.

To follow a live run, poll `GET /v1/agent-runs/{run_id}/history` with `after_sequence` set to the last `sequence` you saw. It returns the events logged since then.

To download the whole log, send `GET /v1/agent-runs/{run_id}/export` with `format` set to `json` (default) or `csv`. The response carries a presigned `download_url` that works for `expires_in` seconds (five minutes) without an `Authorization` header. The response is never cached.

### Answer and steer a run

When a run's `status` is `needs_you`, `needs_you.kind` says what it waits on. To answer, send `POST /v1/agent-runs/{run_id}/answer` with `option_key`, `text` or, for a batch, `accepted_keys`. An API key can answer a `question`. Accepting or rejecting a `checkpoint`, `batch`, `risk_review` or `failure` is a decision for a person, so an API key gets `403 api_key_not_allowed`.

To change a run's course, send `POST /v1/agent-runs/{run_id}/instruct` with `text` and an optional `idempotency_key`. A running run reads it at its next step, and a finished run continues from it. An instruction withdraws a pending proposal, so an API key cannot send one while the run waits on a decision.

`POST /v1/agent-runs/{run_id}/stop` stops a run. `POST /v1/agent-runs/{run_id}/mode` with `mode` switches a live run between `guided` and `background`. Archiving and deleting a run stay in Coverbase.

## Billing overview

`GET /v1/billing-overview` returns your billing `contracts`, each usage `metrics` entry with its limit and usage history, and `as_of`. It is read only. It returns `404 not_enabled` when billing is off for your organization. It needs `billing:read:org`, which API keys do not hold, so use a key created by a person whose role holds it.

## RFPs

These routes change an RFP and work its responses after you create it. To list, read, create, invite, publish, compare or award, use the [RFPs API](/api-reference/rfps). None of these routes emails a vendor.

`GET /v1/rfp-categories` lists the categories your RFPs use, so a new RFP can reuse one.

To change an RFP, send `PATCH /v1/rfp-records/{rfp_id}`. Fields you omit keep their value. Send `null` for a timeline field, `owner_id`, `service_id` or `passing_threshold` to clear it.

`POST /v1/rfp-records/{rfp_id}/pause` puts an RFP back to draft, and `POST .../cancel` cancels it. `POST .../set-status` with `status` moves it to any lifecycle status, such as `in_review` or `shortlisted`. Moving it to `archived` also needs `rfp:archive:org`, and to `awarded` needs `rfp:approve:org`. Both are decisions for a person, so an API key gets `403 api_key_not_allowed`.

`GET /v1/rfp-records/{rfp_id}/invitations` lists the invited vendors. `PATCH .../invitations/{invitation_id}` with `status` and an optional `disqualification_reason` moves one along, for example to `declined` or `disqualified`.

To record a response, send `POST /v1/rfp-records/{rfp_id}/submissions` with `invitation_id` and an optional `response_session_id`. This marks the invitation submitted. `GET .../submissions` lists responses. `POST .../submissions/rank` with `submission_ids`, best first, ranks them by hand; responses you leave out follow in their old order. `POST .../lock-rubric` with an optional `weighting_set_name` and `weights_json` freezes the scoring rubric as a new version.

## Workflow list and lifecycle requirements

`GET /v1/workflow-definitions` lists your automation workflows. Filter with `is_archived` and `is_enabled`, and page with `limit` and `offset`.

`GET /v1/lifecycle-requirements` with `target_type` (such as `vendor`) and `target_id` returns what the record still needs before each workflow-gated status change.

## Integration hub

These endpoints work the [integration hub](/user-guides/integration-hub): your procure-to-pay, CLM and HR connections, their syncs and the steward queue. They need the TPRM lifecycle; without it they return `404` with the code `not_enabled`. `{provider}` is a provider key such as `coupa` or `ironclad`.

`GET /v1/integrations` lists every provider offered to your organization. A connected provider carries its `connection`: `status`, `last_synced_at`, `last_sync_status`, `last_error` and its open conflict and mismatch counts. No credential is ever returned. Connecting a provider, rotating its webhook secret and disconnecting it store or delete a credential, so you do those in Coverbase.

`PUT /v1/integrations/{provider}/status` pauses or resumes a connection with `status` set to `paused` or `active`. `PUT /v1/integrations/{provider}/mappings` replaces its `field_mappings`. A provider you have not connected returns `404` with the code `connection_not_found`, and one not offered to you returns `provider_not_offered`.

`POST /v1/integrations/{provider}/syncs` starts a sync and returns `202 Accepted` with `queued`. Send an optional `object_type` to sync one kind of record. Follow it with `GET /v1/integrations/{provider}/sync-runs`, and see what each run did with every provider record in `GET /v1/integrations/{provider}/sync-records` (filter by `run_id`, `outcome` and `object_type`).

`GET /v1/integration-conflicts` is the steward queue: provider suppliers a sync could not match to one vendor, with their `candidates`. It lists open conflicts unless you pass `status`. `POST .../resolve` links a conflict to the `vendor_id` you send, and the supplier's contracts sync again. `POST .../dismiss` takes it off the queue. `POST /v1/integration-conflicts/bulk-jobs` resolves or dismisses up to 500 conflicts in the background; poll `GET /v1/integration-conflicts/bulk-jobs/{job_id}`.

`GET /v1/integration-mismatches` lists linked supplier fields whose provider value differs from Coverbase's. `POST /v1/integration-mismatches/{mismatch_id}/resolve` settles one with `choice` set to `external`, `coverbase` or `dismiss`. These two need TPRM expansion.

## Monitoring plans

These endpoints work [monitoring plans](/user-guides/monitoring-plans). They need the TPRM lifecycle; without it they return `404` with the code `not_enabled`.

`GET /v1/monitoring-cadence` returns the cadence matrix: for each risk tier (`levels`) and activity, the `interval_months` between runs and the `owner_role`, the reassessment interval per tier, the TPRM Office group and the plan `settings`. `PUT /v1/monitoring-cadence` replaces it with `cells`, `settings` and `tprm_office_department_id`. A cell on a risk level your scale does not have returns `422` with the code `unknown_risk_levels`. Existing plans pick up the new cadence on their next re-plan; an activity someone edited keeps its own interval. Changing the cadence needs `org_settings:update:org`, so use a key created by a person whose role holds it.

`GET /v1/monitoring-plans` lists live plans with each one's next due activity and overdue count. `GET /v1/monitoring-plans/{plan_id}` returns one plan with its `activities`, recent `events`, pending signal moves and last owner attestation. `GET /v1/engagements/{engagement_id}/monitoring-plan` and `GET /v1/services/{service_id}/monitoring-plan` find the plan for a subject; `plan` is null until it is live. `GET /v1/monitoring-plans/{plan_id}/events` returns the plan's history. `GET /v1/monitoring-activities` lists scheduled activities across plans; filter with `activity_types`, `due_window` and `mine`.

`POST .../monitoring-plan/generate` generates a plan now, or re-plans it from the cadence. A service that a live engagement covers returns `409` with the code `covered_by_engagement`, and a paused subject returns `409` with `monitoring_paused`. `PATCH /v1/monitoring-plans/{plan_id}/activities/{activity_id}` changes an activity's `interval_months`, `next_due_at`, `owner_user_id` or `is_enabled`; only the fields you send change. Generating and editing are the TPRM Office's: a caller without org-wide vendor update access gets `403` with the code `not_tprm_office`. `POST .../complete` marks a contract review or evidence request done; other activities complete from their own workflow and return `400` with the code `not_manually_completed`.

Owner attestations, IRQ refreshes, signal moves and scorecards stay in Coverbase.

## Branding

These endpoints read and change your [white-label branding](/user-guides/white-labeling): the logo vendors see on portals and emails, the square icon, the brand color and the vendor portal title. Changes need `org_settings:update:org`, so use a key created by a person whose role holds it.

`GET /v1/branding` returns `full_logo_url`, `icon_url`, `primary_color` and `portal_title`. The logo URLs are public.

`PATCH /v1/branding` changes `primary_color` (a 6-digit hex such as `#0052ff`) or `portal_title`, and removes the logo or icon with `remove_full_logo` or `remove_icon`. A field you omit keeps its value; `null` clears it.

`PUT /v1/branding/logo` and `PUT /v1/branding/icon` upload an image as multipart form data with `file`: PNG, JPG, SVG or WebP, up to 5 MB. Coverbase writes the resized copies vendors see. Any other file returns `422` with the code `invalid_image`. The icon is also your organization's logo at sign-in.

## Workspace logs, notes, email and settings

`GET /v1/activity-log` returns a record's activity log, newest first: field changes, creations, notes and emails. Pass `target_type` and `target_id`, and `related_activity=true` to add the activity of its related records. `GET /v1/audit-log` returns the system audit log (sign-ins, role and permission changes, settings changes, exports and API calls), filtered by time, `event_groups`, `event_types` and `search`, with the total in the `X-Total-Count` header. `GET /v1/audit-log/metadata` lists the groups and types it filters on. An API key needs the `audit:read` scope for both.

`GET /v1/notes` lists the notes on a record with their replies, and `POST /v1/notes` adds one, or a reply with `parent_id`. People a note @mentions are notified. A note on an obligation the vendor is working in a commitment portal also emails the vendor's contacts. `PATCH /v1/notes/{note_id}` replaces the `text` of a note you wrote; people it newly mentions are notified. Archiving a note stays with a signed-in user.

`GET /v1/emails` lists the emails about a record (`object_type` and `object_id`), `GET /v1/emails/search` searches them with `query`, and `GET /v1/emails/{email_id}` returns one. Each needs read access to the record the email is about: for example `vendor:read:org` for a vendor or `contract:read:org` for a contract. `POST /v1/emails` sends an email about a record from your organization's sender. It contacts the recipients: it returns `202 Accepted` with the email `status: queued`, and the email is sent in the background and shows on the record's email log.

`GET /v1/tprm-lifecycle-settings` returns which user groups the TPRM lifecycle routes work to. `GET /v1/template-variables` lists the variables a template can insert; pass exactly one of `surface` or `template_type`. `GET /v1/risk-scales/default` returns your risk scale, and `PUT /v1/risk-scales/default/levels` replaces its `levels`, with a `remap` target for each removed level records still use.

`GET /v1/home-dashboard` names the dashboard you land on at home. `POST /v1/reports/{report_id}/charts/{chart_id}/remove` takes a chart off a dashboard. `POST /v1/reports/{report_id}/scheduled-export/test` sends a dashboard's scheduled export once, to your own address only, from the draft `config` you send.

`POST /v1/performance-scores/from-response` scores a vendor against a rubric from a submitted questionnaire response; Coverbase AI reads the answers and saves the score. `GET /v1/custom-fields/usage` counts how many records hold a value for each custom field. `DELETE /v1/custom-fields/values/{value_id}` clears one value and needs a user key. `POST /v1/directory-people` adds a person who can be named on records and get their email but cannot sign in. `GET /v1/roles/{role_id}/audit-log` lists changes to a role. Creating, changing and archiving roles stays in Coverbase.

## Notifications and saved views

These routes act for the signed-in person. You only ever read or change your own settings, notifications and views. An API key has no settings, notifications or views of its own, so every route in this section gives an API key `403 api_key_not_allowed`. Use a user key.

`GET /v1/notification-settings` lists your setting for each event type and channel, with the default where you have not changed it. `POST /v1/notification-settings` turns one `event_type` on or off for one `channel` with `status`, and returns `201 Created`. `PATCH /v1/notification-settings/{setting_id}` changes a saved setting's `status`. `GET /v1/notification-settings/{setting_id}` returns one. Someone else's setting returns `404` with the code `notification_setting_not_found`. `GET /v1/notification-types` lists every event type you can configure, with its category, name and description.

`GET /v1/notification-preference` says how your email notifications arrive: `delivery_format` is `immediate` or `digest`, with `digest_hour`, `timezone` and `urgent_bypass`. `PUT /v1/notification-preference` sets all four.

`GET /v1/notifications` lists your in-app notifications, with optional `statuses`, `offset` and `limit`. `POST /v1/notifications/mark-seen` marks the `notification_ids` you send as seen. An ID that is not yours returns `404` with the code `notification_not_found`.

`GET /v1/saved-views` lists your saved views of one list, named by `object_type`, and the views shared with your organization. `POST /v1/saved-views` saves a filter, sort and search as a view you own and returns `201 Created`. `PATCH /v1/saved-views/{saved_view_id}` changes one. Only an admin changes a shared view or your organization's default view; anyone else gets `403` with the code `saved_view_not_editable`.

## Email layouts

An email layout is the frame your outgoing emails wear: one for vendors (`external`) and one for your team (`internal`).

`GET /v1/email-layouts` lists the saved layouts. `POST /v1/email-layouts` saves the layout for its `layout_type`, replacing the current one, and returns `201 Created`. `PATCH /v1/email-layouts/{layout_id}` replaces a saved layout's settings.

`GET /v1/email-layouts/{layout_id}/preview` returns the saved layout rendered as `html`, the way a real email renders it, branding included. `POST /v1/email-layouts/preview` renders a layout you have not saved: send its settings with the `logo_url` and `primary_color` filled in. Neither saves or sends anything.

`POST /v1/email-layouts/{layout_id}/dry-run` emails the saved layout's preview to you, and nobody else. It returns `202 Accepted` and the email goes out in the background. An API key has no inbox, so it gets `403` with the code `api_key_not_allowed`.

These routes need organization settings permission. A service account key does not hold it, so use a key created by a person whose role holds it.

## Create and change custom fields

`POST /v1/custom-fields` defines a custom field: `field_name`, `properties` (its `field_type` and settings), and the `applied_to_*` record types it shows on. It returns `201 Created`. A `default_value` in `properties` is filled onto the records the field applies to, and an autofilled field starts filling itself in.

`PATCH /v1/custom-fields/{custom_field_id}` changes the field's name, settings, record types or order. A field you omit keeps its value. `section_id: null` takes the field out of its section. Changing an autofilled field refills it unless you send `backfill: false`. An unknown field returns `404` with the code `custom_field_not_found`.

## Connector settings

`GET /v1/licensed-connectors` lists the licensed data connectors and whether each is configured, and `GET /v1/licensed-connectors/{connector}` returns one. `POST /v1/licensed-connectors/{connector}/test` checks that its key still works; an unconfigured connector returns `404` with the code `connector_not_configured`. These need the TPRM lifecycle.

`GET /v1/third-party-integrations/{provider}` returns a third-party integration's settings as the dashboard shows them, for `slack`, `docusign`, `dnb`, `jira`, `servicenow`, `processunity`, `valence`, `shodan`, `hibp`, `censys` or `screening`. `POST /v1/third-party-integrations/{provider}/test` checks the connection for `slack`, `servicenow`, `processunity`, `valence` and `screening`. The screening test needs `integration:update:org` and returns `ok` and `message`, so a key the provider rejects comes back as `ok: false` rather than an error. `POST /v1/third-party-integrations/slack/test-message` sends your `message` as a real Slack direct message, through your connected workspace, to the Slack account whose email matches the caller. It returns `204`. If Slack is not connected or no Slack account matches, you get `404` with the code `slack_not_found`. An API key acts as its service account, so the message lands only when that account's email matches a Slack user. `POST /v1/jira-tickets` creates a ticket in your connected Jira project. A secret never comes back, only whether it is set. Saving a key or deleting a connection stays in Coverbase.
