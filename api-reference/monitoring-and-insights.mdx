These endpoints give you API access to four monitoring features: Inspect schedules (internal controls monitoring), the document insight review queue, dark web monitoring, and the Certificate Vault.

All endpoints are scoped to the API key's organization. See [API conventions](/conventions) for shared behavior. List endpoints take `limit` and `offset` and return `items`, `total`, `limit`, and `offset`.

Each feature has its own gate. When your organization does not have the feature, its endpoints return `404` with one of these codes:

| Code | Feature |
| ---- | ------- |
| `inspect_not_enabled` | Inspect |
| `dark_web_not_enabled` | Dark web monitoring |
| `certificates_not_enabled` | Certificate Vault |

When your organization enforces roles and the key lacks the permission, the endpoint returns `403`.

Some actions stay with a signed-in person. When an API key calls one of them, the endpoint returns `403` with the code `api_key_not_allowed`. These actions are: archiving or restoring a document insight (one at a time or in bulk), unlinking a custom field from an insight, resetting a dark web playbook, retiring a decision model, deleting an insight group or target, stopping an Inspect schedule, removing a watchlist identifier, marking a certificate `verified`, archiving a certificate, archiving a rule set, deleting an insight example or value, archiving or restoring an org document, deleting a document insight, rejecting a pending change, creating dark web roles, confirming a dark web setup step, provisioning or deprovisioning an Okta or Entra inspection identity, and rejecting or manually completing an access removal request. API keys never change roles.

## Create and manage document insights

To create an insight, send `POST /v1/document-insights`. It returns `201` with the insight.

<ParamField body="field_name" type="string" required>
  The insight's name, for example "Governing law".
</ParamField>

<ParamField body="field_key" type="string">
  A stable key. Defaults to `field_name`. A key already in use returns `409` with `field_key_exists`.
</ParamField>

<ParamField body="field_description" type="string">
  What to extract and how.
</ParamField>

<ParamField body="field_type" type="string" default="string">
  `string`, `number`, `date`, or `boolean`.
</ParamField>

<ParamField body="field_mode" type="string" default="extraction">
  `extraction` quotes the document; `synthesis` writes text from it.
</ParamField>

<ParamField body="document_types" type="string[]">
  Document types the insight reads. Empty means all.
</ParamField>

<ParamField body="group_id" type="string">
  The insight group to file it under.
</ParamField>

<ParamField body="update_policy" type="string" default="auto_fill">
  `auto_fill`, or `review_required` to hold each change for a reviewer.
</ParamField>

<ParamField body="reviewer_user_id" type="string">
  The reviewer for `review_required` changes.
</ParamField>

To change an insight, send `PATCH /v1/document-insights/{config_id}` with the fields to change. Send `reviewer_user_id: null` to clear the reviewer. `apply_mode` decides what the new definition reaches: `forward_only` (the default) re-runs nothing, `selected` re-runs the documents in `document_ids`, and `all_historical` re-runs every in-scope document an older revision filled. A re-run starts in the background and its id comes back as `backfill_id`; poll `GET /v1/document-insight-backfills/{backfill_id}`. When a running backfill or a daily ceiling blocks the re-run, nothing is saved and the response is `409`, `422`, or `429` with `backfill_refused`. Making a synthesis insight anything but text returns `422` with `synthesis_needs_text`.

To edit many insights at once, send `POST /v1/document-insights/bulk-update` with `config_ids` (up to 200) and any of `enabled`, `group_id`, `clear_group`, `add_document_types`, and `remove_document_types`. Document types are added and removed, never replaced. To archive many at once, send `POST /v1/document-insights/bulk-archive` with `config_ids`; API keys cannot do this. Both return `updated_count` and the changed insights in `items`.

To retire an insight and keep its values, send `POST /v1/document-insights/{config_id}/archive`. To bring it back, send `POST /v1/document-insights/{config_id}/restore`.

### Targets

A target links an insight to a built-in contract or document field it fills. To list them, send `GET /v1/document-insights/{config_id}/targets`. To add one, send `POST /v1/document-insights/{config_id}/targets` with `object_type` (`contract` or `vendor_document`), `field_name`, and optionally `conflict_policy` (`fill_if_empty`, `latest_document_wins`, `never_overwrite`), `min_confidence` (`low`, `medium`, `high`), `require_grounded`, and `enabled`. A pairing no parser covers returns `422` with `target_not_supported`; a field the insight already fills returns `409` with `target_exists`.

To change a target, send `PATCH /v1/document-insight-targets/{target_id}`. To stop filling the field, send `DELETE /v1/document-insight-targets/{target_id}`. Values already written stay.

### Groups

To list groups, send `GET /v1/document-insight-groups`. To create one, send `POST /v1/document-insight-groups` with `name` and optionally `description`, `document_types`, `sort_order`, and `enabled`. To change one, send `PATCH /v1/document-insight-groups/{group_id}`; changing `document_types` rescopes every insight that inherits from the group. To delete one, send `DELETE /v1/document-insight-groups/{group_id}`. Its insights stay, outside any group.

### Coverage

`GET /v1/document-insight-stats` returns one row per insight with how many eligible documents it applies to, how many hold a value, and its fill rate. Pass `config_id` one or more times to read only those insights.

## Correct a vendor's external security scan

## Teach a document insight with examples

A worked example shows an insight an excerpt and the answer it should give. An enabled example is part of what extraction is asked, so each change starts a new revision of the insight.

- To list examples, send `GET /v1/document-insights/{config_id}/examples`.
- To add one, send `POST /v1/document-insights/{config_id}/examples` with `document_excerpt`, `expected_value` (the answer in the insight's type, or null for "not in the document"), and optionally `explanation`, `document_id`, and `enabled`. An answer that does not fit the insight's type returns `422` with `invalid_expected_value`.
- To change one, send `PATCH /v1/document-insight-examples/{example_id}`. Only the fields you send change.
- To delete one, send `DELETE /v1/document-insight-examples/{example_id}`.
- To build an example from an extracted value, send `POST /v1/document-insight-values/{data_id}/to-example` with an optional `explanation`. A value that cites no document text returns `422` with `no_cited_text`.

## Escalate an exposure, sync the watchlist, and set retention

- To open a finding from an exposure, send `POST /v1/dark-web/exposures/{exposure_id}/escalate` with optional `title` and `assigned_to_id`. A second call returns the same `finding_id`.
- To re-derive the watchlist from your organization and vendor records now, send `POST /v1/dark-web/watchlist/sync`. The response counts identifiers `created`, `kept`, and `archived`.
- To read how long each class of dark web data is kept, send `GET /v1/dark-web/retention`. To change it, send `PUT /v1/dark-web/retention` with `exposures_years`, `evidence_years`, `audit_years`, and `sweep_history_years`. A shorter period purges older data at the next nightly run.

## Work with your organization's own documents

Org documents are files your organization owns, such as policies, questionnaire and report templates, and exports.

- To list them, send `GET /v1/org-documents` with optional `document_type`, `search`, `limit`, and `offset`.
- To download one, send `GET /v1/org-documents/{document_id}/download`. The response gives a presigned `url` that is valid for `expires_in` seconds. Follow it with a plain `GET` and no auth header.
- To rename, retype, archive, or restore one, send `PATCH /v1/org-documents/{document_id}` with any of `name`, `document_type`, and `is_archived`.
- To upload one, send `POST /v1/org-documents` as `multipart/form-data` with `file` and optional `document_type` and `name`. It returns `201` with the document. An `assessment_report_template` must be a valid `.docx`: another extension returns `400` with `template_must_be_docx`, and a file that does not open as Word returns `400` with `invalid_template`.

## Correct or remove extracted values

- To replace an extracted value with the right one, send `POST /v1/document-insight-values/{data_id}/correct` with one of `value_string`, `value_number`, `value_date`, or `value_boolean`. The correction becomes a manual value that no re-extraction overwrites, and Coverbase writes it to linked fields. A value that does not fit the insight's type returns `422` with `invalid_value`.
- To delete a value, send `DELETE /v1/document-insight-values/{data_id}`.
- To judge many values at once, send `POST /v1/document-insight-values/bulk-verdict` with `ids` and `verdict` (`correct`, `incorrect`, or null). The response gives `updated_count` and `found_count`; a value that already holds the verdict is skipped.

## Fill a custom field from a document insight

Promoting an insight links it to a custom field on vendors, services, assessments, or contracts, so each extracted value also fills that field.

- To see which custom fields an insight could fill, send `GET /v1/document-insights/{config_id}/promotion-options`. `compatible_field_type` names the custom field type the insight can fill, or is null when its type cannot fill one yet. Each item gives `custom_field_id`, `field_name`, `field_type`, `applied_to`, and `is_linked`.
- To link it, send `POST /v1/document-insights/{config_id}/promote` with either `custom_field_id` (an existing field) or `new_field_name` and `applied_to` (`vendor`, `service`, `assessment`, or `contract`) to create one. Optional fields are `require_grounded` (default `true`), `min_confidence` (`high`, `medium`, or `low`; default `medium`), `conflict_policy` (`never_overwrite`, `fill_if_empty`, or `latest_document_wins`; default `fill_if_empty`), and `backfill` (default `true`, which fills the field from existing documents in the background). The response gives `custom_field_id`, `created_custom_field`, and `backfill_queued`. An archived insight returns `409` with `document_insight_archived`, a field that already has another autofill source returns `409` with `custom_field_has_autofill_source`, and a type or target mismatch returns `422` with `promotion_invalid`.
- To stop filling a field, send `DELETE /v1/document-insights/{config_id}/custom-fields/{custom_field_id}`. It returns `204`. Values already written stay. A field the insight does not fill returns `409` with `custom_field_not_linked`.

## Train a decision model

A decision model is the model document insight extraction uses for your organization. You can start one from a base model, train it on your verified values, and switch extraction to it once it scores at least as well as the standard model. Responses never include storage locations or job identifiers.

- To list models, send `GET /v1/document-insight-models`. The response also gives `base_model_ids` you can start from, `active_model_id`, and `training_configured`.
- To start one, send `POST /v1/document-insight-models` with `name` and `base_model_id`. An unlisted base model returns `422` with `base_model_not_allowed`.
- To collect verified values into its training set, send `POST /v1/document-insight-models/{model_id}/dataset`. `dataset_stats` gives the counts.
- To compare it with the standard model, send `POST /v1/document-insight-models/{model_id}/evaluate` with an optional `max_documents` (1 to 100, default 25). It returns `202` and costs model calls. Poll the list until `eval_result.status` is no longer `running`.
- To start fine-tuning, send `POST /v1/document-insight-models/{model_id}/training`. Training runs for hours. To record its progress, send `POST /v1/document-insight-models/{model_id}/training/sync`.
- To switch extraction to it, send `POST /v1/document-insight-models/{model_id}/activate`. A trained model is held back until its accuracy check passes; `activation_blocked_reason` says why.
- To retire it, send `POST /v1/document-insight-models/{model_id}/retire`. Retiring the active model returns extraction to the standard model. API keys cannot retire.

A step the model's state refuses, such as evaluating a retired model or training without a dataset, returns `409` with `decision_model_conflict`.

## Manage saved sign-in sessions

Inspect saves a sign-in session (an auth context) per single sign-on provider or application, and reuses it across runs. ## Read Okta and Entra connections

- To list the applications synced from Okta, send `GET /v1/okta-integration/applications`. For Microsoft Entra, send `GET /v1/entra-integration/applications`. Both take `limit` (1 to 500, default 100) and `offset`. Each item has `id`, `provider_app_id`, `display_name`, `status`, `sign_on_mode`, `login_url`, `platform_key`, `vendor_id`, and `last_synced_at`.
- To read how often Coverbase syncs Okta, send `GET /v1/okta-integration/schedule`. The response has `connected`, `sync_interval_hours`, `last_synced_at`, and `next_sync_at`.
- To change it, send `PUT /v1/okta-integration/schedule` with `sync_interval_hours` set to `6`, `12`, `24`, or `168`, or null to sync only when someone asks.
- To read the latest sync, send `GET /v1/okta-integration/sync`. The response has `job`, which is null when Okta never synced. A job has `id`, `kind`, `status`, `stage`, `incremental`, `inventory_ready`, `applications_ready`, `applications_total`, `access_synced_count`, `groups_synced_count`, `can_resume`, record counts, `last_error`, `started_at`, and `completed_at`. - To read one Okta application, send `GET /v1/okta-integration/applications/{application_id}`. The response has its sign-on mode, whether Inspect can sign in to it, its assignment count, and its vendor link. It leaves out the raw Okta record, which can hold credentials. To list who is assigned to it, send `GET /v1/okta-integration/applications/{application_id}/users`.
- To list the people in your Okta directory with their application accounts and findings, send `GET /v1/okta-integration/identities` with `limit` (1 to 500, default 100) and `offset`. For counts only, send `GET /v1/okta-integration/identities/summary`.

## Run probes

A probe is a custom check Inspect runs on one application, once as a preview or on a schedule. Each run is a sample.

1. To draft a probe, send `POST /v1/inspect-probes/prepare` with `target_id` (the application), `objective`, and an optional `name`. Inspect plans checkpoints from the platform's documentation. Nothing is saved.
2. To save the draft, send `POST /v1/inspect-probes` with the draft's `draft_id`, `target_id`, `name`, `resource_bundle_id`, and `spec`, and an optional `interval_seconds` (900 to 604800, default 3600). It returns `201` with the probe, paused.
3. To run a sample now, send `POST /v1/inspect-probes/{probe_id}/preview` with an `idempotency_key`. It returns `202` with the sample's `inspection_id` and `run_id`. Sending the same key again returns the first sample.
4. To turn on its schedule, send `PATCH /v1/inspect-probes/{probe_id}/automation` with `enabled: true` and an optional `interval_seconds`. Inspect needs a reviewed preview of the current procedure and every requirement ready, or the call returns `409`.

To change the procedure, send `POST /v1/inspect-probes/{probe_id}/versions` with `expected_version` (the `version` you read), `resource_bundle_id`, and `spec`. When someone published since, it returns `409`.

- To list probes, send `GET /v1/inspect-probes` with an optional `application_id`, `limit` (1 to 100, default 25), and `offset`. To filter them, send `POST /v1/inspect-probes/query` with `filter`, `sort`, `search`, `application_id`, `limit`, and `offset`. The response has `probes` and `total`.
- To read one probe with its procedure, readiness, automation, and latest sample, send `GET /v1/inspect-probes/{probe_id}`.
- To list samples, send `GET /v1/inspect-probes/{probe_id}/runs`. To read one sample with each checkpoint's result and its evidence, send `GET /v1/inspect-probes/{probe_id}/runs/{run_id}`.
- To keep a sample for an auditor, send `GET /v1/inspect-probes/{probe_id}/runs/{run_id}/package`. It returns a zip with a manifest, a printable summary, and the screenshots. `X-Missing-Screenshots` counts screenshots Coverbase could not read. The response is never cached.
- To see each scheduled launch and whether a sample started, send `GET /v1/inspect-probes/{probe_id}/deliveries` with optional `before`, `after`, `exclude_accepted`, and `limit`.

The `definitions` routes are deprecated. New probes do not need a definition.

## Export, import, and test insight definitions

- To export your insight library, send `GET /v1/document-insight-definitions` with an optional `include_archived`. Each item is a portable definition keyed by `field_key`, with no ids and no extracted values.
- To import definitions, send `POST /v1/document-insight-definitions` with `definitions` (up to 500) and an optional `overwrite_existing` (default `false`). An insight whose `field_key` already exists is skipped unless you overwrite. The response lists `created_field_keys`, `updated_field_keys`, and `skipped_field_keys`.
- To try a definition before saving it, send `POST /v1/document-insight-definitions/test` with `field_name` and any of `field_description`, `field_type`, `field_mode`, `document_types`, `sample_size` (1 to 5), `config_id`, and `document_ids`. ## Delete a document insight

Deleting removes the insight and every value it ever extracted. It cannot be undone, so it takes two steps.

1. Archive the insight with `POST /v1/document-insights/{config_id}/archive`.
2. Send `GET /v1/document-insights/{config_id}/delete-preview`. The response gives `extracted_value_count` and `linked_custom_field_names`.
3. Send `DELETE /v1/document-insights/{config_id}?acknowledged_value_count=N`, where `N` is the count the preview gave. It returns `204`.

API keys cannot delete an insight. An insight that is not archived returns `409` with `insight_not_archived`, a count that changed returns `409` with `value_count_changed`, and an insight that still fills a custom field returns `409` with `linked_custom_fields`. Unlink those fields first.

## Read value history and coverage

- To read every value change for one insight, newest first, send `GET /v1/document-insights/{config_id}/events` with `limit` (1 to 200) and `offset`. For one value's timeline, send `GET /v1/document-insight-values/{data_id}/events`. Each item gives `event_type`, `trigger`, `actor_name`, `document_name`, `before`, and `after`.
- To read every recorded revision of a definition, send `GET /v1/document-insights/{config_id}/revisions`.
- To read the coverage matrix, send `GET /v1/document-insight-coverage` with optional `document_type` and `config_id`, each repeatable. `rows` gives each document type's totals, and `cells` gives each insight's `eligible`, `filled`, `grounded`, `needs_review`, `never_attempted`, and `fill_rate` per type.
- To see what waits for a person, send `GET /v1/document-insight-inbox`. It counts `field_changes`, `disagreements`, `unverified_evidence`, and `accuracy_misses`.
- To list the built-in contract and document fields an insight can fill, send `GET /v1/document-insight-target-fields`.

## Browse and compare extracted values

- To filter every value in your organization, send `POST /v1/document-insight-values/query` with any of `config_ids`, `document_types`, `vendor_ids`, `source_type`, `confidence`, `grounded`, `needs_review`, `has_value`, `search`, `verdict`, `outdated`, `config_revision`, `limit` (1 to 200), and `offset`.
- To compare values side by side, send `POST /v1/document-insight-values/pivot` with `document_types` (1 to 20) and optional `config_ids`, `vendor_ids`, `search`, `limit`, and `offset`. Each row is a document, and `cells` maps each insight ID to its value. A missing key means nothing was extracted.

### Evidence images

- To list a value's verified citations, send `GET /v1/document-insight-values/{data_id}/snippets`. Each item gives `evidence_fingerprint`, the quote and page, and `status`. A `rendered` citation carries a presigned `url` to its page image, valid for `expires_in` seconds. Follow it with a plain `GET` and no auth header.
- To render a citation's image, send `POST /v1/document-insight-values/{data_id}/snippets` with `evidence_fingerprint`. It returns `queued` and renders in the background. List the snippets again for the link. A fingerprint that matches no current citation returns `404` with `citation_not_found`.

## Export an insight's values

- To list the columns an export can hold, send `GET /v1/document-insight-export-columns`.
- To export, send `POST /v1/document-insights/{config_id}/export` with any of `columns`, `data_ids`, the value filters, `include_empty`, and `multi_value_mode`. The response gives a presigned `url` to the workbook, `filename`, `expires_in`, `exported_rows`, and `available_rows`. Every export is recorded on the insight's activity.

These responses are never cached.

## Check a decision model's accuracy

- To read a check's scorecard, send `GET /v1/document-insight-models/{model_id}/scorecard`. It gives `base`, `candidate`, and `shadow` scores, overall and per insight, with reviews applied.
- To work through the misses, send `GET /v1/document-insight-models/{model_id}/examples` with optional `role`, `config_id`, `outcome`, `reviewed`, `limit`, and `offset`.
- To settle one miss, send `POST /v1/document-insight-eval-examples/{example_id}/review` with `decision` (`team_right`, `ai_right`, `both_fine`, or null to clear). `ai_right` also corrects the checked value to the AI's answer, which needs `vendor:update` on that vendor.
- To see one insight's training set, send `GET /v1/document-insight-models/{model_id}/dataset-preview?config_id=...` with an optional `status` (`train`, `holdout`, `used_as_example`, or `no_evidence`).
- To answer live documents with a trained model beside production, send `PUT /v1/document-insight-models/{model_id}/shadow` with `enabled`. Only one model shadows at a time, and nothing it answers is saved. A model that is not trained and ready returns `409` with `shadow_unavailable`.

## Run an insight on a document

- To run a saved insight on one document, send `POST /v1/documents/{document_id}/insight-extractions` with `config_id`. It costs one model call, returns the answer with its quote and confidence, and saves nothing.
- To try an unsaved definition, send `POST /v1/documents/{document_id}/insight-previews` with `field_name` and optional `field_description`, `field_type`, and `field_mode`. It returns `202` with a job. Poll `GET /v1/document-insight-previews/{job_id}` until `status` is `completed` or `failed`. Only the key or person that started a preview reads it.

## Retrain the document type model

Your organization's document type model is a fork of a shared base model. To read where both stand, send `GET /v1/document-type-decision-model`. To retrain your fork, send `POST /v1/document-type-decision-model/train-fork`. It returns `202`. A run already in progress returns `409` with `training_running`, and a missing base model returns `409` with `base_model_missing`. Without the feature, both return `404` with `document_type_model_not_enabled`.

## Reject a pending change

To reject a proposed field change, send `POST /v1/document-insight-pending-changes/{change_id}/reject`. Nothing is written to the target record. An already resolved change returns `409` with `change_already_resolved`. API keys cannot approve or reject changes, so a signed-in person does it.

## Work an exposure

- To read one exposure, send `GET /v1/dark-web/exposures/{exposure_id}`. It adds the playbook, `baseline_item_id`, and `follow_up_finding_id` to the list fields. The matched value stays masked, and opening an exposure is audited. For its status history, send `GET /v1/dark-web/exposures/{exposure_id}/history`.
- To read its playbook, send `GET /v1/dark-web/exposures/{exposure_id}/playbook`. To tick or untick a step, send `PATCH` to the same path with `step_id` and `done`. A step that is not on the playbook returns `422` with `step_not_on_playbook`.
- To move many held exposures at once, send `POST /v1/dark-web/exposures/bulk-review` with `exposure_ids` (up to 200), `action` (`promote` or `dismiss`), and, to dismiss, `false_positive_reason`. Only exposures still in Needs review move. The rest come back in `skipped` with `not_found` or `not_in_needs_review`.
- To read evidence, send `GET /v1/dark-web/exposures/{exposure_id}/evidence`. Each capture gives its metadata and a presigned `download_url` for the redacted capture, valid for `expires_in` seconds. The content is never inline, every read is audited, and the response is never cached.
- To start a follow-up with a partner, send `POST /v1/dark-web/exposures/{exposure_id}/partner-follow-up` with optional `title`, `assigned_to_id`, and `note`. It opens a finding on the exposure's vendor, or on the partner a program BIN runs for. It does not contact the partner: whether and how the partner hears stays your decision. A second call returns the open finding with `created` set to `false`.
- To read one vendor's dark web picture, send `GET /v1/dark-web/vendors/{vendor_id}`.

Recording consent and sending an exposure to Legal never go through the API.

## Run the dark web program

- To run a sweep now, send `POST /v1/dark-web/sweeps`. It returns `202`. One sweep runs at a time, so a second call returns `active_run_id`. To list sweeps, send `GET /v1/dark-web/sweeps`.
- To read the setup checklist, send `GET /v1/dark-web/setup`. To record that a person reviewed the alert rules or the business hours, send `POST /v1/dark-web/setup/confirm/{confirmation}` with `alert_rules_reviewed` or `business_hours`. API keys cannot confirm a step.
- To preview a retention change, send `GET /v1/dark-web/retention/preview` with any of `exposures_years`, `evidence_years`, `audit_years`, and `sweep_history_years`. It counts what the next purge removes and gives `next_purge_at`.
- To read the program report, send `GET /v1/dark-web/report` with `from_ts`, `to_ts`, and optional `time_zone`. It returns aggregates only. Each read is audited.
- To export the queue, send `POST /v1/dark-web/exposures/export` with the queue filters. The response gives a presigned `url` to a CSV with no summary, matched value, or evidence. More than the export limit returns `413` with `export_too_large`.
- To read the sources, send `GET /v1/dark-web/sources`. To read the managed AI fraud terms, send `GET /v1/dark-web/ai-fraud-terms`.

### Baseline

The baseline is the list of exposures your organization already knew about.

- To read a file's columns, send `POST /v1/dark-web/baseline/preview` as `multipart/form-data` with `file` (`.csv` or `.xlsx`). It suggests a mapping and stores nothing.
- To import, send `POST /v1/dark-web/baseline/import` as `multipart/form-data` with `file`, `mapping` (a JSON object from each baseline field to a column), and `dry_run`. `dry_run` defaults to `true`, so send `false` to keep the import. A re-import replaces every item.
- To read the baseline, send `GET /v1/dark-web/baseline`. Identifiers are masked.

### Alert rules

- To list the rules in evaluation order, send `GET /v1/dark-web/alert-rules`.
- To add one, send `POST /v1/dark-web/alert-rules` with the whole rule: `name`, `is_enabled`, `applies_in_addition`, `match`, `recipients`, `channels`, `clock`, and `escalation`. To replace one, send `PATCH /v1/dark-web/alert-rules/{rule_id}` with the whole rule. To set the order, send `PUT /v1/dark-web/alert-rules/order` with `rule_ids`. These need an organization admin.
- To see how often a rule would have fired, send `POST /v1/dark-web/alert-rules/preview` with `match`. It counts exposures first seen in the last 30 days.
- To check your SIEM's parser, send `POST /v1/dark-web/alert-rules/test`. It sends a fictional, signed `DarkWebExposure.Created` to every webhook subscribed to dark web events, so it contacts your webhook endpoints.

### Access

To read the roles that open dark web monitoring and what each can do, send `GET /v1/dark-web/access`. To create the designated roles your organization is missing, send `POST /v1/dark-web/access/roles`. It never changes a role that exists. API keys never change roles.
