The Risk API gives you the same risk register, scenarios and reports the Risk page shows. A **risk** is an entry on the register with an inherent and a residual score, an owner, a scope and the signals (findings, contract gaps, alerts and other records) that support it.

Every endpoint is scoped to the organization of the API key. See [API conventions](/conventions) for shared behavior.

The `/v1/risks`, `/v1/risk-exposure`, `/v1/risk-report`, `/v1/risk-config` and `/v1/risk-scenarios` endpoints need the Risk module. When your organization does not have it, they return `404` with the code `not_enabled`.

Endpoints that need `org_settings:read:org` or `org_settings:update:org` work with a user API key. A service account key does not hold `org_settings`, so it receives `403` from them in an organization that enforces roles.

Archiving a risk or a scenario, and deciding on a risk the Coverbase agent proposed, stay decisions a signed-in user makes in the app. The API does not offer them.

## Errors

Errors return a `detail` object with a `code` and a `message`.

| Status | Code | When |
| ------ | ---- | ---- |
| `403` | | The key's role does not hold the permission the endpoint needs. |
| `404` | `not_enabled` | The Risk module is not enabled for your organization. |
| `404` | `risk_not_found` | No risk has that ID. |
| `404` | `signal_not_found` | The risk has no signal with that ID. |
| `404` | `scenario_not_found` | No saved scenario has that ID. |
| `404` | `risk_domain_not_found` | No risk domain has that ID. |
| `404` | `job_not_found` | No narrative or suggestion job you started has that ID. |
| `422` | `invalid_risk` | The risk is missing a description or a score is off the scale. |
| `400` | `invalid_risk_domain` | The risk domain change is not valid, for example a duplicate name. |
| `404` | `commitment_not_found` | No commitment has that ID. |
| `404` | `finding_not_found` | No finding has that ID. |
| `404` | `document_not_found` | The finding or commitment has no document with that ID. |
| `400` | `round_action_not_available` | The commitment's round does not offer that action, or no round awaits you. |
| `400` | `commitment_not_editable` | The commitment cannot take that edit, for example an archived commitment. |
| `400` | `commitment_has_no_finding` | The commitment belongs to an obligation, so it takes no documents here. |
| `422` | `invalid_upload` | The uploaded file is empty or too large. |
| `400` | `invalid_finding_source` | The bulk create's source does not exist or does not fit the rows. |

## Query the register

<ParamField path="method" type="POST">
  `POST /v1/risks/query`
</ParamField>

Returns one page of register risks that match the filters. Send an empty body to list every risk except closed ones.

<ParamField body="statuses" type="string[]">
  Any of `proposed`, `open`, `mitigating`, `accepted` and `closed`.
</ParamField>

<ParamField body="risk_domain_ids" type="string[]">
  Risk domains to include.
</ParamField>

<ParamField body="vendor_id" type="string">
  Only risks scoped to this vendor.
</ParamField>

<ParamField body="search" type="string">
  Text to match in the risk description.
</ParamField>

<ParamField body="limit" type="integer" default="25">
  Page size. The API caps it at 200.
</ParamField>

<ParamField body="offset" type="integer" default="0">
  Rows to skip.
</ParamField>

The body also accepts `categories`, `owner_user_ids`, `owner_department_ids`, `unowned`, `appetite`, `source_types`, `institution_key`, `service_id`, `contract_id`, `finding_id`, `review_overdue`, `proposal_kinds` and `sort`.

### Response

```json
{
  "items": [
    {
      "id": "cbrisk_...",
      "description": "Loss of the payments processor halts checkout",
      "status": "open",
      "inherent_score": 20,
      "residual_score": 12,
      "appetite": "outside",
      "owner": { "user_id": "cbuser_...", "display": "Dana Lee" },
      "signal_counts": { "open": 3, "closed": 1, "dismissed": 0 }
    }
  ],
  "total": 1,
  "limit": 25,
  "offset": 0
}
```

## Read the register summary and matrix

<ParamField path="method" type="GET">
  `GET /v1/risks/summary`
</ParamField>

Returns the register's headline numbers: risks outside appetite, open proposals, unowned risks, overdue reviews, open signals, and counts by domain, source and category.

<ParamField path="method" type="GET">
  `GET /v1/risks/matrix`
</ParamField>

Returns the likelihood by impact heat map with inherent and residual counts per cell.

<ParamField query="institution_key" type="string">
  Limit either view to one institution of a multi-entity organization.
</ParamField>

<ParamField query="risk_domain_id" type="string">
  For the matrix, limit to one risk domain.
</ParamField>

## Create a risk

<ParamField path="method" type="POST">
  `POST /v1/risks`
</ParamField>

Returns `201 Created` with the new risk and its computed scores.

<ParamField body="description" type="string" required>
  What could happen.
</ParamField>

<ParamField body="risk_domain_id" type="string">
  The risk domain the risk belongs to.
</ParamField>

<ParamField body="likelihood_level" type="integer">
  Inherent likelihood on your organization's scale. `impact_level`, `residual_likelihood_level` and `residual_impact_level` work the same way.
</ParamField>

<ParamField body="owner_user_id" type="string">
  The owning user. Use `owner_department_id` to name a business unit instead.
</ParamField>

<ParamField body="vendor_ids" type="string[]">
  Vendors in scope. `service_ids`, `department_ids`, `entity_ids` and `region_codes` set the rest of the scope.
</ParamField>

The body also accepts `category`, `status`, `treatment`, `treatment_plan`, `review_at`, `accepted_until`, `institution_key` and `note`.

## Get or edit a risk

<ParamField path="method" type="GET">
  `GET /v1/risks/{risk_id}`
</ParamField>

Returns one risk with its signals, history and the excerpt of the dependency chain behind it.

<ParamField path="method" type="PATCH">
  `PATCH /v1/risks/{risk_id}`
</ParamField>

Takes the same fields as create. Fields you omit keep their value. Returns the updated risk.

## Attach or dismiss a signal

<ParamField path="method" type="POST">
  `POST /v1/risks/{risk_id}/signals`
</ParamField>

Returns `201 Created` with the attached signal.

<ParamField body="source_type" type="string" required>
  One of `finding`, `contract`, `contract_clause`, `contract_component_gap`, `obligation`, `screening_match`, `radar_signal`, `radar_alert`, `vendor_risk_change`, `inspect_evaluation`, `assessment` and `supplier_site`.
</ParamField>

<ParamField body="source_id" type="string" required>
  The ID of the record.
</ParamField>

<ParamField body="rationale" type="string">
  Why the record supports this risk.
</ParamField>

<ParamField path="method" type="POST">
  `POST /v1/risks/{risk_id}/signals/{signal_id}/dismiss`
</ParamField>

Dismisses the signal and returns it. The signal stays on the risk's history.

## Read exposure, the board report and the configuration

<ParamField path="method" type="GET">
  `GET /v1/risk-exposure`
</ParamField>

Returns appetite gauges per risk domain, the loss model, the contractual cushion, and fourth party, business unit and geographic concentration. Pass `institution_key` to limit the domain gauges to one institution.

<ParamField path="method" type="GET">
  `GET /v1/risk-report`
</ParamField>

Returns the board report: KRI tiles, movers, appetite breaches, domains, framework coverage and commitments on time. Pass `period` with a key from the response's `periods` to read an earlier period.

<ParamField path="method" type="GET">
  `GET /v1/risk-config`
</ParamField>

Returns the Risk module configuration: appetite thresholds, taxonomy, quantification, likelihood and impact levels, domain appetite, signal sources and agent settings.

## Run and save scenarios

<ParamField path="method" type="POST">
  `POST /v1/risk-scenarios/run`
</ParamField>

Runs a what-if scenario over the dependency chain and returns its blast radius, obligations, findings on the path and loss estimate. Nothing is saved.

<ParamField body="inputs" type="object" required>
  The scenario. Set `kind` to `event`, `change` or `offboard`, name the subject with `subject_vendor_id` or `subject_node_id`, or send a plain-English `prompt` such as "Okta is down for 24 hours".
</ParamField>

<ParamField path="method" type="POST">
  `POST /v1/risk-scenarios`
</ParamField>

Returns `201 Created` with the saved scenario. Send `inputs`, an optional `title`, and the `result` of a run. When you omit `result`, Coverbase runs the scenario once and saves what it returns, which also needs `risk:run:org`.

<ParamField path="method" type="GET">
  `GET /v1/risk-scenarios`
</ParamField>

Lists saved scenarios, newest first, with `limit` (at most 200) and `offset`.

<ParamField path="method" type="GET">
  `GET /v1/risk-scenarios/{scenario_id}`
</ParamField>

Returns one saved scenario with its inputs and result.

## Finding acceptance rules

Acceptance rules decide who recommends, who decides and who approves when a finding's risk is accepted. The first rule that matches a finding's severity routes it. The rule endpoints need the TPRM lifecycle and return `404` with the code `not_enabled` otherwise.

`GET /v1/finding-acceptance-rules` lists the rules in the order they are checked.

`POST /v1/finding-acceptance-rules` returns `201 Created` with a new rule. Send `name`, and optionally `match_level_ids` (severity level IDs; empty matches every severity), `recommender_department_id`, `decider_department_id`, `extended_acceptance_days` with `extended_approver_user_id`, and `sort_order`. Without `sort_order` the rule is checked last. A user group or approver that does not exist, or a threshold sent without an approver, returns `400` with the code `invalid_rule`.

`PUT /v1/finding-acceptance-rules/{rule_id}` replaces a rule with the same body. A field you leave out is cleared, so send every value the rule should keep. `PUT /v1/finding-acceptance-rules/order` takes `rule_ids`, every live rule in the new order.

`GET /v1/findings/{finding_id}/decision-path` returns where a finding stands: `phase`, the routing rule in `route`, the `decisions` so far, and `can_recommend`, `can_decide` and `can_approve` for the key's user. Without the TPRM lifecycle it returns `enabled: false`.

## AI narratives and suggestions

The app writes these texts as you watch. Through the API you start a job and poll it, since the model takes a few seconds to answer.

Each start call returns `202 Accepted` with the job's `id`, its `kind` and `status: pending`. Poll `GET /v1/text-jobs/{job_id}` until `status` is `completed` or `failed`. A completed job carries `result`; a failed one carries `error_message`. You can read only jobs you started.

`POST /v1/risk-narrative/jobs` writes a report's narrative and saves it as the report's narrative, as **Regenerate** does in the app. Send `report_type`, and optionally `scope_key`, `subject_id` and `regenerate`. Unless you set `regenerate`, a saved narrative that is still fresh, or one a person edited, comes back completed at once. Its `result` is the saved narrative: `content`, `title`, `generated_at` and `is_user_edited`. It needs the Risk module.

`POST /v1/finding-suggestions` suggests a finding's `title`, `description` or levels (`finding_levels_bundle`) from an assessment. Send `assessment_id`, `field_name`, `suggest_context` (`evals` or `document_requirement`), `eval_ids`, and optionally the `existing_finding_levels` already chosen. When every level is already chosen, the job completes at once. An unknown assessment returns `404` with the code `assessment_not_found`.

`POST /v1/vendor-finding-suggestions` makes the same suggestion for a vendor finding raised from a Radar alert. Send `vendor_id`, `field_name` and `radar` (`alert_id`, `severity`, `summary` and `detector_name`). An unknown vendor returns `404` with the code `vendor_not_found`.

`POST /v1/commitment-description-suggestions` suggests a commitment description. Send a `finding_id`, or `obligation_ids` with an optional `vendor_id`, and optionally `source` (`finding` or `obligation`). An unknown finding returns `404` with the code `finding_not_found`.

A suggestion's `result` is `{"text": ...}`: the model's answer inside `<output>`, with a `<value>` and a short `<reasoning>`, or the chosen level IDs for `finding_levels_bundle`. Nothing is saved on a finding or commitment; you apply the text yourself.

## Send commitments to a vendor

## Edit a commitment and answer the vendor's round

`PATCH /v1/commitments/{commitment_id}` edits a commitment's terms, status or assignee. A field you omit keeps its value, and `null` clears it. Changing terms the vendor already accepted reopens their round on the portal, with your optional `revision_message`. A status change notifies the finding's people. Archiving or unarchiving with `is_archived` needs a user key; an API key gets `403` with the code `api_key_not_allowed`.

`POST /v1/commitments/{commitment_id}/resolve-round` answers the vendor's latest round with one of the two actions the commitment's `round_actions` offers:

| Action | What it does |
| ------ | ------------ |
| `accept` | Closes the commitment. |
| `accept_risk` | Accepts the vendor's decline and closes the commitment. |
| `adopt_terms` | Takes the vendor's proposed due date; mitigation starts. |
| `request_more_work` | Rejects a completion; the round reopens and mitigation stays underway. |
| `re_request` | Rejects a decline or a compensating control; back to negotiating. |
| `hold_terms` | Keeps your terms and sends them back. |

A send-back reopens the vendor's round on the portal with your `message`. Nobody is emailed. `note` is kept as an internal comment. `accept`, `accept_risk`, `adopt_terms` and `request_more_work` are decisions, so an API key gets `403` with the code `api_key_not_allowed`. An action the round does not offer returns `400` with the code `round_action_not_available`.

## Commitment and finding documents

`GET /v1/findings/{finding_id}/documents` lists a finding's documents: its own, then each of its commitments'. A commitment's documents carry its `commitment_id`. `GET /v1/commitments/{commitment_id}/documents` lists one commitment's documents.

`POST .../documents` attaches a file as multipart form data with `file`, and an optional `note`. It returns `201 Created`. `PATCH .../documents/{document_id}` replaces the `note`; `null` clears it. `POST .../documents/{document_id}/archive` takes a document off. An uploaded document is archived, while a vendor document stays in the vendor's library. Archiving needs a user key.

A document never carries its storage location. `GET .../documents/{document_id}/download` returns a `url` to download it, valid for an hour, with `Cache-Control: no-store`.

## Create findings in bulk

`POST /v1/findings/bulk` creates up to 50 findings on one source. Send `source_type` (`assessment`, `vendor` or `org_document`), `source_id` and `rows`. Each row has your own `client_row_id` and a `title`, and optionally `body`, `assigned_to_id`, `vendor_id`, `due_date`, `eval_ids`, `finding_status_id` and the level IDs. A row from a document's finding extraction sends `approved_candidate_id`, and `extraction_source_document_id` on an assessment.

Each row lands or fails on its own. The response has the created findings in `data`, and each failed row's `client_row_id` and `reason` in `failed_records`. An unknown source returns `400` with the code `invalid_finding_source`. Assignees and the finding's people are emailed once each. The vendor is not.
