A **portal** (`cbsbpt_...`) is one request sent to a vendor: an assessment's document collection and its follow-ups, a questionnaire, a findings and commitments request, an RFP, a case follow-up, or onboarding. Each request has its own link. These endpoints list the requests so your own systems can show a vendor everything still waiting on them, or sync request status into a partner portal, a CRM, or a ticketing tool.

The endpoints return only requests addressed to a vendor. Org-level portals (intake, vendor search), signing portals, and obligation commitments sent to your own stakeholders are never returned.

All endpoints are org-scoped to the credential: an `ak_*` key or an [OAuth token](/api-reference/oauth), and need permission to read portals. See [API conventions](/conventions) for shared behavior.

| Method | Path |
| ------ | ---- |
| `GET` | `/v1/portals` |
| `GET` | `/v1/portals/{portal_id}` |
| `GET` | `/v1/portals/{portal_id}/questionnaires` |

## States

Each request carries a `state`, derived from its status, its due date, and whether you have paused it:

| State | Meaning |
| ----- | ------- |
| `open` | Waiting on the vendor. Includes a request you have paused and one whose answers are being analyzed. |
| `overdue` | Open, past its `due_at`, and not paused. |
| `submitted` | The vendor has submitted their response. |
| `closed` | You closed the request. |

`open` and `overdue` are the two states that need the vendor's attention.

## Request types

| `type` | What the vendor is asked for |
| ------ | ---------------------------- |
| `assessment` | Documents for an assessment, and its follow-up questions. |
| `informational` | A questionnaire with no assessment attached. |
| `irq` | An inherent risk questionnaire. |
| `findings_commitment` | Remediation commitments on findings you have shared. |
| `vendor_onboarding` | Onboarding details for a new vendor. |
| `rfp` | An RFP prequalification or response. |
| `case` | A follow-up on a monitoring case. |

## The link is not a credential

`url` is the same link the invitation email carries. Opening it still asks the recipient to sign in with an email address the request allows, so the link identifies the request; it does not grant access to it. Share it with the people you invited and it works the way the email did.

<Tip>
  If you want each vendor to have one address for everything, turn on the [centralized supplier portal](/user-guides/centralized-supplier-portal). Every request keeps its own `url`, and the vendor also gets a single page listing all of them.
</Tip>

## List portals

<ParamField path="method" type="GET">
  `GET /v1/portals`
</ParamField>

Lists requests in the API key's org, newest first. Without filters it returns every request addressed to a vendor, paginated.

### Query parameters

<ParamField query="vendor_id" type="string">
  Only requests sent to this vendor (`cbvndr_...`). Resolve the id first with [`GET /v1/vendors`](/api-reference/vendors#list-vendors) by `external_id` or `name`.
</ParamField>

<ParamField query="state" type="string">
  Only requests in this state: `open`, `overdue`, `submitted`, or `closed`.
</ParamField>

<ParamField query="type" type="string">
  Only requests of this [type](#request-types).
</ParamField>

<ParamField query="limit" type="integer" default="50">
  Page size, 1-200.
</ParamField>

<ParamField query="offset" type="integer" default="0">
  Rows to skip.
</ParamField>

### Example request

```bash cURL
curl "https://api.coverbase.app/v1/portals?vendor_id=cbvndr_e448ba62882143f3ba0c140bb2e30162&state=open" \
  -H "Authorization: Bearer ak_live_xxx"
```

### Example response

```json
{
  "items": [
    {
      "id": "cbsbpt_9c1f0e2a7b3d4e5f8a6b7c8d9e0f1a2b",
      "reference": "WF-855",
      "type": "assessment",
      "state": "open",
      "status": "open",
      "url": "https://dashboard.coverbase.app/portal/k3x9q2m8v1",
      "display_name": "Annual security review",
      "vendor_id": "cbvndr_e448ba62882143f3ba0c140bb2e30162",
      "assessment_id": "cbassm_1f2e3d4c5b6a79880a1b2c3d4e5f6a7b",
      "due_at": 1762300800,
      "paused": false,
      "submitted_at": null,
      "created_at": 1760313600,
      "forms_total": 3,
      "forms_completed": 1,
      "percent_complete": 33
    }
  ],

  "limit": 50,

```

Rows are ordered by `created_at` descending, with ties broken by `id`, so paging with `offset` never repeats or skips a row.

### Portal object

<ResponseField name="id" type="string">Portal ID (`cbsbpt_...`).</ResponseField>
<ResponseField name="reference" type="string | null">A short reference the vendor also sees, such as `WF-855`. Set once the [centralized supplier portal](/user-guides/centralized-supplier-portal) is on; `null` otherwise.</ResponseField>
<ResponseField name="type" type="string">The [request type](#request-types).</ResponseField>
<ResponseField name="state" type="string">`open`, `overdue`, `submitted`, or `closed`. See [States](#states).</ResponseField>
<ResponseField name="status" type="string">The stored status: `open`, `analyzing`, `analysis_complete`, `submitted`, or `closed`. Use `state` unless you need to tell the three open statuses apart.</ResponseField>
<ResponseField name="url" type="string">The link the vendor uses to respond. On a branded portal domain, the link uses that domain.</ResponseField>
<ResponseField name="display_name" type="string | null">The request's title as the vendor sees it.</ResponseField>
<ResponseField name="vendor_id" type="string">The vendor the request was sent to (`cbvndr_...`).</ResponseField>
<ResponseField name="assessment_id" type="string | null">The assessment this request collects for (`cbassm_...`), for `assessment` requests.</ResponseField>
<ResponseField name="due_at" type="integer | null">Unix timestamp (seconds) the response is due, or `null` when no due date was set.</ResponseField>
<ResponseField name="paused" type="boolean">`true` while you have put the request on hold. A paused request reads `open`, never `overdue`, and no reminders go out.</ResponseField>
<ResponseField name="submitted_at" type="integer | null">Unix timestamp (seconds) of the vendor's first submission, or `null`.</ResponseField>
<ResponseField name="created_at" type="integer">Unix timestamp (seconds).</ResponseField>
<ResponseField name="forms_total" type="integer">How many forms the request asks for: each questionnaire, document upload, or other section the recipient sees. A form you have withdrawn from the request is not counted.</ResponseField>
<ResponseField name="forms_completed" type="integer">How many of those forms the recipient has completed. A form resubmitted after a reopen counts once.</ResponseField>
<ResponseField name="percent_complete" type="integer | null">`forms_completed` as a whole-number share of `forms_total`, rounded down (1 of 3 is `33`). `null` for a request with no forms. A form counts only once it is submitted, so a request with two forms reads `0`, `50`, or `100`.</ResponseField>

The three progress fields are the same progress the Coverbase app shows on the request. For how many questions the recipient has answered, across the whole request or per questionnaire, read `questions_percent_complete` from [Questionnaire progress on a portal](#questionnaire-progress-on-a-portal).

## Retrieve a portal

<ParamField path="method" type="GET">
  `GET /v1/portals/{portal_id}`
</ParamField>

Returns the [portal object](#portal-object), or `404 portal_not_found`. A portal that the list would not return (one with no vendor, or of a type outside the [request types](#request-types)) is also a `404`.

### Error responses

| Status | Body | When |
| ------ | ---- | ---- |
| 404 | `{"detail": {"code": "portal_not_found", ...}}` | Not found, not in the API key's org, or not a vendor request. |

## Questionnaire progress on a portal

<ParamField path="method" type="GET">
  `GET /v1/portals/{portal_id}/questionnaires`
</ParamField>

Returns one row per questionnaire on the request, with how many of its questions the recipient has answered, and `questions_percent_complete` for the request as a whole. Use it when the portal's `percent_complete` is too coarse: a request with one questionnaire reads `0` until the recipient submits, while this endpoint shows the questionnaire filling in question by question.

### Path parameters

<ParamField path="portal_id" type="string" required>
  The portal (`cbsbpt_...`). Same `404 portal_not_found` rules as [Retrieve a portal](#retrieve-a-portal).
</ParamField>

### Example request

```bash cURL
curl "https://api.coverbase.app/v1/portals/cbsbpt_9c1f0e2a7b3d4e5f8a6b7c8d9e0f1a2b/questionnaires" \
  -H "Authorization: Bearer ak_live_xxx"
```

### Response fields

<ResponseField name="portal_id" type="string">The portal the rows belong to.</ResponseField>
<ResponseField name="items" type="array">One row per questionnaire on the request. See [Questionnaire progress row](#questionnaire-progress-row).</ResponseField>
<ResponseField name="questionnaires_total" type="integer">How many questionnaires the request asks for.</ResponseField>
<ResponseField name="questionnaires_completed" type="integer">How many of them the recipient has submitted: the row's `status` is `submitted`, `ready_for_review`, or `approved`.</ResponseField>
<ResponseField name="percent_complete" type="integer | null">`questionnaires_completed` as a whole-number share of `questionnaires_total`, rounded down. `null` for a request with no questionnaires.</ResponseField>
<ResponseField name="counted_questions_total" type="integer">The questions progress is measured against, across every questionnaire on the request. Each questionnaire adds its required questions, or all of its questions when none is required. This is the same set each row's `percent_complete` counts.</ResponseField>
<ResponseField name="counted_questions_answered" type="integer">How many of those questions have an answer.</ResponseField>
<ResponseField name="questions_percent_complete" type="integer | null">`counted_questions_answered` as a whole-number share of `counted_questions_total`, rounded down (32 of 37 is `86`). This is how far the recipient has got on the whole request. `null` when there is nothing to count.</ResponseField>

### Questionnaire progress row

<ResponseField name="questionnaire_id" type="string">The questionnaire template (`cbqst_...`).</ResponseField>
<ResponseField name="questionnaire_name" type="string | null">The questionnaire's name as the recipient sees it.</ResponseField>
<ResponseField name="response_id" type="string | null">The recipient's response (`cbqstr_...`), or `null` until they have opened the questionnaire. Pass it to [`GET /v1/questionnaires/{questionnaire_id}/responses/{response_id}`](/api-reference/questionnaires#get-a-submission) for the answers themselves.</ResponseField>
<ResponseField name="status" type="string | null">The response's status: `pending`, `processing`, `processing_complete`, `processing_failed`, `submitted`, `ready_for_review`, `approved`, or `rejected`. `null` until the recipient has opened the questionnaire.</ResponseField>
<ResponseField name="questions_total" type="integer">Questions the recipient sees. Internal-only questions, and questions a show rule currently hides, are left out. A questionnaire derived from a control set counts its controls' questions. `0` until the recipient has opened the questionnaire.</ResponseField>
<ResponseField name="questions_answered" type="integer">How many of those questions have an answer. See [What counts as answered](#what-counts-as-answered).</ResponseField>
<ResponseField name="required_total" type="integer">How many of the questions are required.</ResponseField>
<ResponseField name="required_answered" type="integer">How many required questions have an answer.</ResponseField>
<ResponseField name="percent_complete" type="integer | null">`required_answered` as a whole-number share of `required_total`, rounded down (20 of 25 is `80`). When no question is required it is `questions_answered` over `questions_total` instead. `null` when there is nothing to count: the recipient has not opened the questionnaire, or it has no questions.</ResponseField>
<ResponseField name="last_activity_at" type="integer | null">Unix timestamp (seconds) the response last changed, or `null` for a questionnaire the recipient has not opened.</ResponseField>

### What counts as answered

A question is answered by the same rule the recipient's **Submit** button uses: it has a text or numeric value, a selected option, or an attached document where the question requires one. A comment alone does not count unless the question requires a comment.

Only questions the recipient can currently see are counted, the same as the progress bar on their side. A question a show rule hides is left out until an answer reveals it. Because of this, a count can go down: answering a question can reveal more required questions.

If you archive the control set behind a questionnaire while a request is still open, that questionnaire's row reads `0` counts and `null` percent. The other rows and the request totals still answer.

### Error responses

| Status | Body | When |
| ------ | ---- | ---- |
| 404 | `{"detail": {"code": "portal_not_found", ...}}` | Not found, not in the API key's org, or not a vendor request. |

## Show a vendor their open requests

The common integration: a partner or vendor portal of your own that lists everything Coverbase is waiting on from one vendor.

<Steps>
  <Step title="Resolve the vendor">
    `GET /v1/vendors?external_id=<your id>` returns the Coverbase `vendor_id` for the identifier your system holds. Match by `name` if you have not set `external_id` on your vendors yet.
  </Step>
  <Step title="Fetch what is waiting">
    `GET /v1/portals?vendor_id=<vendor_id>&state=open`, then the same call with `state=overdue`. Or fetch without `state` and group rows by it, which also gives you the submitted and closed history.
  </Step>
  <Step title="Show the link">
    Render each row's `display_name`, `due_at`, and `url`. Mark `overdue` rows and `paused` rows so the reader knows which ones need action now.
  </Step>
  <Step title="Show how far each request has got">
    For each open or overdue row, call `GET /v1/portals/{portal_id}/questionnaires` and read `questions_percent_complete`. A low number close to `due_at` is the request to follow up on.
  </Step>
</Steps>

Poll on a schedule that suits you; the list is cheap. To react to a change as it happens instead, subscribe to `Assessment.*` events with [webhooks](/integrations/webhooks#event-catalog).
