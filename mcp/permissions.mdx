The Coverbase MCP server does not have its own permission system. Every tool call runs as the person who authorized the connection, with the access that person has in Coverbase at that moment. There are no separate MCP permissions to configure and no service identity that sees more than the user.

This page explains how that works end to end: how a request is authenticated, how the user's role and permissions are resolved, and how reads and writes are checked.

<Note>
  **The short version.** Three things decide access: the **role and permissions** of the identity connecting, the **scopes** on the credential, and your **confirmation** of each write.

  - If your organization **enforces roles and permissions**, the server checks the same permissions the dashboard checks, tool by tool and record by record. A user who sees only their assigned records in the dashboard sees only those records through MCP. Custom roles can connect and get exactly their role's permissions.
  - If it **does not**, access follows the default role: **Admins** and **Members** can write, and **Guests** and **Siloed Members** are read-only.

  An API key can also be minted **read-only**, which withholds write regardless of role. Role and permission changes take effect on the user's next request, for every kind of credential.
</Note>

## Permission inheritance

When a client connects, the user signs in to Coverbase through OAuth 2.0 and authorizes the connection. From that point on, every tool the assistant calls is evaluated against **that user's live organization membership**: their current role and, where your organization enforces roles and permissions, that role's current permissions. The connector is a delegate, not a privileged service account.

Three properties follow from this design:

<CardGroup cols={3}>
  <Card title="No privilege escalation" icon="user-lock">
    Changes made through the assistant are never broader than what the connected user could do in the dashboard, and with roles and permissions enforced, neither are reads.
  </Card>

  <Card title="Single source of truth" icon="database">
    Permissions are read from the user's organization membership and role on every request, not from a static config baked into the connector or copied at install time.
  </Card>

  <Card title="Org isolation" icon="building-shield">
    Every call is scoped to the user's organization. The client never supplies an organization ID; the server derives it from the authenticated session.
  </Card>
</CardGroup>

## Role-to-access matrix

What a role can do through MCP depends on whether your organization enforces roles and permissions. See [Permissions and roles](/user-guides/permissions-and-roles) for how roles and custom roles are set up.

### When your organization enforces roles and permissions

Each tool checks the permission that the matching dashboard action checks.

| Role | Can connect to MCP? | Reads | Writes |
| --- | --- | --- | --- |
| **Admin** | Yes | Everything | Everything, with confirmation |
| **Member**, **Siloed Member**, **Guest** | Yes | What the role's permissions allow | What the role's permissions allow, with confirmation |
| **Custom role** | Yes | What the role's permissions allow | What the role's permissions allow, with confirmation |
| **Auxiliary Member** | No | - | - |
| **Service Account** | API key only | What the service account role allows | No (read-only) |

- **Reads follow record scope.** A role that reads only the records assigned to it (for example, `vendor:read:assigned`) gets only those records from every list, search, report and count. Asking for a record outside that scope by its id is refused. A role with no read access to a kind of record is told so instead of getting an empty list.
- **Writes follow the same permissions.** Updating a vendor needs vendor update access, and with assigned-only access, the vendor has to be one assigned to you. Remove a permission from a role and the matching write is refused through MCP as it is in the dashboard. A Guest or Siloed Member can make the changes the dashboard lets them make on records assigned to them, such as review decisions and work queue items.
- **A few writes have no dashboard permission of their own**, such as creating a department, a site or a work queue item. Through MCP, those stay limited to Admins, Members and custom roles.
- **Service Accounts** are held to the service account role's permissions and never write through MCP.

### When your organization does not enforce roles and permissions

| Role | Can connect to MCP? | Read tools | Write tools |
| --- | --- | --- | --- |
| **Admin** | Yes | Yes | Yes |
| **Member** | Yes | Yes | Yes |
| **Siloed Member** | Yes | Yes | No (read-only) |
| **Guest** | Yes | Yes | No (read-only) |
| **Auxiliary Member** | No | - | - |
| **Custom role** | No | - | - |
| **Service Account** | API key only | Yes, within the service account role's permissions | No (read-only) |

- **Write access** (creating or updating vendors, assessments, Zero Touch runs, control sets and controls, Radar sources, detectors, signals and cases, findings, obligations, notes, tags, and other records) is reserved for **Members** and **Admins**. The [tool reference](/mcp/tool-reference#writes) lists every write entity and action.
- **Custom roles** cannot connect, because a custom role's permissions only apply once your organization enforces roles and permissions. The server refuses the connection with `403` rather than guessing. Give the user one of the default roles above, or enforce roles and permissions.

In both modes:

- **Auxiliary Members** cannot use the MCP server at all, and receive a `403` if a token for one is ever presented.
- **Service Accounts** are non-interactive by design, so they cannot sign in through OAuth or a dashboard session; those paths return `403`. They *can* hold an API key, which is what makes a programmatic read-only connection possible without a human seat.
- **Only active members connect.** An invited member who has not joined yet, or a member who was deactivated or removed, is refused with `403` and the message "Your membership in this organization is no longer active."

## How a request is authorized

Every request flows through the same gate, regardless of which client or token type it uses. There is no path that skips it.

<Steps>
  <Step title="Authenticate the token">
    The server accepts three token formats on the `Authorization: Bearer` header: an OAuth 2.0 access token issued to a remote MCP client, a dashboard SSO session token, or a long-lived Coverbase-issued MCP API key. Anything else is rejected with `401`.
  </Step>

  <Step title="Resolve the live membership">
    The user's membership is read from Coverbase on **every request**, for every token type. The membership has to be active, and the role comes from it, never from anything stored in the token or the client. A custom role resolves to that role's current permissions.
  </Step>

  <Step title="Enforce the connect allowlist">
    If the resolved role cannot connect (see the [matrix](#role-to-access-matrix)), the request is rejected with `403` before any tool runs.
  </Step>

  <Step title="Check the tool and the records">
    Each tool checks the user's access before it reads or changes anything. With roles and permissions enforced, that is the permission the matching dashboard action needs, narrowed to assigned records where the role is. Writes then pass through the guard described in [Write protection](#write-protection).
  </Step>

  <Step title="Scope to the organization">
    The organization is taken from the authenticated session and applied to every query automatically. The client cannot widen the scope by passing a different organization ID; there is no parameter to do so.
  </Step>
</Steps>

When a check refuses a call, the assistant gets a short explanation, such as "You don't have permission to update vendors in Coverbase." or "You can only see the vendors assigned to you, and this one isn't." Nothing is read or changed. The message does not name the permission or the role.

## Write protection

A write only executes when **three independent conditions** are all satisfied. Any one of them failing returns a clear, non-destructive error instead of performing the change.

<Steps>
  <Step title="Permission check (least privilege)">
    With roles and permissions enforced, the user needs the permission the matching dashboard action needs, on that specific record. Without enforcement, the user's role must be **Member** or **Admin**; Guests and Siloed Members are told their role cannot run write tools.
  </Step>

  <Step title="Scope check">
    The credential must carry the **`mcp:write`** scope. An API key minted read-only, or an OAuth token issued without it, produces a strictly read-only connection even for a user whose role would otherwise allow writes. (See [Scopes](#scopes).)
  </Step>

  <Step title="Explicit confirmation (human-in-the-loop)">
    Every write tool requires an explicit `confirm=true` argument. Without it, the tool returns a precondition error rather than executing, so the assistant is forced to surface the proposed change to you and wait for your approval before anything is written.
  </Step>
</Steps>

Most writes check permission before asking for confirmation, so you are not asked to approve a change you cannot make. A few administrative actions check right after you confirm; if the check fails they refuse, and nothing is written.

<Warning>
  These checks are applied **server-side**, before any database write. They do not rely on the client or the model behaving correctly. A misbehaving or compromised client cannot bypass the permission check, the scope check, or the confirmation requirement.
</Warning>

## Scopes

The server defines two scopes:

| Scope | Grants |
| --- | --- |
| `mcp:read` | Access to all read tools (search, detail, reports). |
| `mcp:write` | Access to write tools, in combination with a write-capable role and explicit confirmation. |

Every credential carries `mcp:read`. Whether it also carries `mcp:write` is fixed when the credential is issued:

- **API keys** store their scopes on the key itself. Tick **Read-only** when you generate one under **Configuration → MCP Server** and the key never carries `mcp:write`, not now and not if the owner is promoted to Admin later. The key list shows the grant on each key.
- **OAuth tokens** are issued with both scopes by default. The authorization endpoint also accepts a narrower `scope` request, so a client can ask for `mcp:read` alone.

<Note>
  A read-only credential is not merely refused at the last moment. The `mutate` tool is **hidden** from such a connection: it does not appear in the client's tool list, and `mcp_capabilities` reports no mutations. The same goes for a Guest or Siloed Member where roles and permissions are not enforced, and for a service account key. With roles and permissions enforced, `mutate` is listed for every other write-scoped connection, and each write action refuses on its own if the user lacks the permission.
</Note>

## Programmatic read-only access

The common case is a pipeline, a scheduled report, or an internal assistant that should read Coverbase and never change it. You do not need a human seat for this.

<Steps>
  <Step title="Generate the key as an admin">
    Go to **Configuration → MCP Server** and choose **New API key**.
  </Step>
  <Step title="Choose what the key acts as">
    **Service account** is the usual answer: a built-in non-human identity that needs no seat in your identity provider and never signs in. Choose **Another user** instead to attribute the key's activity to a particular member, such as a Guest kept for reporting.

    Either choice makes the key **read-only automatically**. A key that authenticates as someone else can never write, so a change is never recorded under a name that did not make it.
  </Step>
  <Step title="Store the key">
    The secret is shown once. Send it as `Authorization: Bearer cb_mcp_...` from your client. See [Connecting clients](/mcp/connecting).
  </Step>
</Steps>

<Info>
  You keep control of a key you minted for a service identity: it appears in your key list and you can revoke it, even though it authenticates as something else. For what shows up in the audit trail once it is running, see [Attributing a key that acts as a service account](#attributing-a-key-that-acts-as-a-service-account).
</Info>

<Note>
  **Want a guaranteed read-only connection?** Any one of these is sufficient on its own, because the write guard requires *both* write access through the role *and* the write scope:

  1. Mint the API key **read-only**.
  2. Bind the key to a **service account** or another user, which forces read-only.
  3. Where your organization does not enforce roles and permissions, connect with a **Guest** or **Siloed Member** account; their role blocks writes regardless of scope. Where it does, use a role that holds no create, update or archive permissions.
</Note>

## Live revalidation

Because access is resolved from live membership on every request, changes you make in Coverbase propagate without any re-install or token re-issuance on the user's side.

- **Every credential** (API key, session token and OAuth token) re-reads the user's membership, role and permissions on each request. A demotion, a permission removed from a role, or a removal from the organization applies to the very next tool call.
- **A key's scopes do not follow the role.** A read-only key stays read-only through any promotion, which is what makes it safe to hand to an automation.

<Info>
  A demotion is also a downgrade of MCP access, and a removal is a revocation, without anyone needing to touch the connector. Revoking an MCP API key under **Configuration → MCP Server** stops it at once. Disconnecting a client removes the tokens that client holds.
</Info>

## What this means in practice

<AccordionGroup>
  <Accordion title="A Siloed Member asks the assistant for every critical vendor" icon="filter">
    With roles and permissions enforced and a role that reads only assigned vendors, the assistant gets the critical vendors assigned to that user, and the counts in any summary match. Asking for another vendor by its id is refused with a message that it is not assigned to them.
  </Accordion>

  <Accordion title="A Guest asks the assistant to update a vendor" icon="circle-xmark">
    Without roles and permissions enforced, the update is **blocked by the role check**. With them enforced, it succeeds only if the Guest's role holds vendor update access to that vendor. Either way, a refused update changes nothing.
  </Accordion>

  <Accordion title="A Member asks the assistant to create a finding" icon="circle-check">
    The permission check passes and the default token carries `mcp:write`. The assistant proposes the new finding and waits. Once you confirm, it re-runs the tool with `confirm=true` and the finding is created, and the action is recorded in the audit trail.
  </Accordion>

  <Accordion title="An admin removes a permission from a role" icon="sliders">
    With roles and permissions enforced, every user holding that role loses the matching tool access on their next request, through any credential. There is nothing to reconfigure on their machines.
  </Accordion>

  <Accordion title="A user is removed from the organization" icon="user-xmark">
    Their next request fails with a `403` on every kind of credential, including an OAuth connection whose access token has not expired yet.
  </Accordion>
</AccordionGroup>

## Auditability

Every tool call, read or write, is logged with the connected identity, the tool name, the parameters, a timestamp, and the outcome. Write actions taken through the MCP server land in the same Coverbase audit trail as actions taken in the dashboard, so administrators have one consolidated record of who did what, regardless of whether it happened through the UI or an assistant.

### Attributing a key that acts as a service account

A reasonable question about any non-human credential: if it changes something, whose name is on it?

For MCP keys the answer is that it cannot change anything. A key bound to a service account or to another user is read-only, and a service account can never write through MCP. **A bound key never produces a write in your audit trail**, so there is no such thing as a change you cannot trace to a person. Only a key that acts as *you* can write, and those entries carry your name exactly as if you had made the change in the dashboard.

What you can still see for a bound key:

<CardGroup cols={2}>
  <Card title="Who provisioned it" icon="user-check">
    Creating and revoking an MCP key are recorded in **Configuration → Audit Logs** under **Integrations**, attributed to the admin who did it, with the key's name. The key also stores that admin internally, so a key always traces back to a person even though it runs unattended.
  </Card>

  <Card title="What it read, and when" icon="list-check">
    Every tool call the key makes is logged with the connected identity, the tool, the arguments, and the outcome. Read activity is recorded, not only writes.
  </Card>
</CardGroup>

<Warning>
  **One service account identity is shared by every integration in your organization**, and it is the same identity behind your REST API keys. Two MCP keys bound to it are not distinguishable from each other in the per-call logs, which record the identity rather than the individual key.

  So issue **one key per integration** rather than reusing a single key across several, and give each a name that says what it is for. That way the provisioning record in the audit log tells you which integration was set up when and by whom, and revoking one key stops exactly one integration instead of all of them at once.
</Warning>

<Info>
  This differs from the [REST API](/conventions#public-api-audit-log), where each request records the calling `ak_` key's id and name alongside the shared identity. Per-key attribution on individual MCP tool calls is not available today.
</Info>

<Note>
  If you need machine activity attributed to a distinct named identity rather than the shared service account, bind the key to a dedicated user instead: create a **Guest** for it and use **Another user** when generating the key. That costs a seat in your identity provider, which the service account option avoids, so it is a trade between attribution granularity and provisioning overhead.
</Note>
