The server exposes **12 tools**. Nine of them are read dispatchers, one per domain, each covering many operations through a `kind` parameter. One returns reports, one performs every write, and one describes the rest. Together they route 393 read kinds, 32 reports, and 626 write actions.

The server keeps the tool count small because an assistant choosing among hundreds of narrowly named tools spends its context on the choice and still picks wrong. A dozen tools with explicit routes leave more room for your data.

Everything you can do in the dashboard has a route here, with a few exceptions that need a file upload, a file download, or an email the server cannot send. Each guide says which tasks stay in the dashboard.

<Tip>
  You rarely need this page to *use* the server. Ask for what you want in plain language and the assistant picks the route. This is here for when you want to know exactly what it can reach, audit what an assistant did, or write a prompt that names a specific call.
</Tip>

## Reads

Each read tool takes a `kind` and the identifiers that kind needs. All are read-only and scoped to your organization and your permissions.

Every read tool, and `get_report`, also accepts `params`: a JSON object for any parameter a kind takes that the tool does not name. For example, `query_assessments(kind="zero_touch", assessment_id="cbqsrw_...", params={"version": 2})` reads an earlier version of a revised Zero Touch result. A named argument wins over the same key in `params`. `mcp_capabilities()` lists the parameters of every kind.

Reading a long AI analysis: `eval_detail` renders the AI's reasoning whole up to a generous cap. If an analysis is longer than that, the response says so and names the follow-up call that returns the rest: pass `full_text=true` for every section at maximum length, or `analysis_offset` to page through the analysis from a given character. A capped response always announces itself, so a partial analysis is never presented as the complete reasoning.

Reading a long summary report: `summary` works the same way. Pass `full_text=true`, or `summary_offset` (and `recommendation_offset` for the recommendation section), to page through a report longer than one response can carry. The truncation notice names the exact call that returns the next window.

### Risk scores and your scoring settings

Two settings under **Configuration → Scoring** change what every read returns, matching what the Consolidated Assessment Report export drops:

| Setting off | Effect |
| ----------- | ------ |
| Residual risk tracking | Residual risk is omitted everywhere, level and score alike. A workspace that turns this off does not compute the value, so the stored numbers are whatever the last computation left behind. |
| Numerical scores | Raw inherent and residual risk **numbers** are omitted and the named levels stay. The assessment score percent is a separate column and is unaffected. Vendors are still ranked by inherent risk in the portfolio report, without the score printed. |

## Writes

Every write goes through one tool: `mutate(entity, action, data)`. The per-action parameters go inside `data`. The tables below list every entity and action, grouped by area. `mcp_capabilities()` lists the fields each action accepts.

Each write checks the same permission as the matching dashboard action. A write your role cannot make returns an error and changes nothing.

<Warning>

</Warning>

A few of these carry behaviour worth knowing:

<AccordionGroup>
  <Accordion title="vendor / create refuses by default" defaultOpen icon="triangle-exclamation">
    Creating a vendor directly requires `skip_intake: true` in addition to `confirm: true`. Requests to add, buy, or start using a vendor are supposed to go through `intake_session / create` instead, which links or creates the vendor itself. Creating one first leaves a duplicate carrying no due diligence.

    The separate flag exists because a generic "yes, create it" is not the same as accepting that due diligence is being skipped.
  </Accordion>

  <Accordion title="control / update tunes AI evaluation guidance" icon="sliders">
    Editing a control's expectation, evaluation instructions, or evidence requirement changes how the AI judges it. Material edits create a new version rather than overwriting. Pair it with `get_report(report_name="control_flag_rates")` to find the controls worth tuning, and `assessment / rerun` to re-evaluate against the new instructions.
  </Accordion>

  <Accordion title="eval / update triages one control evaluation" icon="check-double">
    Set `outcome` to `not_an_issue` to clear a false positive, `issue` to flag or reopen one, `mitigated` for a real gap the vendor fixed, or `risk_accepted` for one your organization chose to live with, and attach `review_notes`. Closing an issue does not change the score. This is the per-control correction, distinct from the whole-assessment sign-off in `review / create`.
  </Accordion>

  <Accordion title="engagement / archive is terminal" icon="box-archive">
    There is no unarchive.
  </Accordion>

  <Accordion title="rfp authoring writes nothing until create" icon="wand-magic-sparkles">
    `draft_brief`, `research_vendors`, `suggest_requirements` and `generate_questions` return proposals and change nothing. `create` is the one write, and it builds the RFP, its rubric, its questionnaire, the vendor records and the invitations in a single transaction. The RFP lands as a draft; no vendor is contacted until `publish`.
  </Accordion>

  <Accordion title="rfp / simulate_submissions produces research, not responses" icon="user-secret">
    A silent RFP researches how each invited vendor would most plausibly answer, from public information. Nobody is contacted, no vendor has agreed to any of it, and every rendering says so. Vendors who already sent a real response are skipped, and a re-run never deletes a real answer.
  </Accordion>

  <Accordion title="custom_field / set_value needs a config ID first" icon="table-columns">
    Setting a value takes a `custom_field_config_id`, and select fields only accept one of their configured option labels. Both come from `query_platform(kind="custom_fields")`.
  </Accordion>

  <Accordion title="Unknown fields are rejected, not ignored" icon="shield-check">
    Writes reject unexpected keys in `data` and return the accepted set. Silently dropping a misspelled `vender_id` would turn a typo into a successful mutation that quietly omits the field you meant to set.
  </Accordion>
</AccordionGroup>

## Discovery

`mcp_capabilities()` takes no arguments and returns a JSON document enumerating every route above with its parameters: name, type, required or optional, and default value.

It's the recommended first call when an assistant isn't sure which route applies, and it's always current, because it's generated from the running server rather than maintained by hand.
